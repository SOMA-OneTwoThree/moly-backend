# 몰리 백엔드 현재 상태

> 최종 확인: 2026-08-14. 현재 저장소 코드, 연결된 dev/prod DB를 읽기 전용으로 대조했다.

이 문서는 완료된 전환 절차가 아니라 **지금 실제로 쓰는 구조와 남은 운영 과제**만 적는다.

## 1. 배포 상태

대화·장기 기억·관계·사용자별 대화 약속·비동기 잡 구조는 **운영 전환과 사용자 승격까지 끝났고 실제 사용자 요청을 처리 중**이다. 예전 정규화 기억 테이블과 `vecs.memories`는 제거됐다.

2026-08-14 읽기 전용 확인값:

| 항목 | prod |
|---|---:|
| `profiles` | 786 |
| `messages` | 49,154 |
| 삭제되지 않은 `diaries` | 9,703 |
| `memory_pipeline_states` | 729 |
| `mode='v2'`, `bootstrap_status='ready'` | 729 |
| 대화에 노출 가능한 기억(`active`·`ambiguous`) | 10,292 |

`app_config`에서 `agent_enabled=true`, `agent_canary_pct=100`도 확인했다. 즉 운영 사용자는 일기 회상·루틴 조회 도구를 사용할 수 있다. 나머지 설정은 DB에 덮어쓴 값이 없으면 배포 환경변수와 `app/config.py` 기본값을 따른다.

최근 7일 잡에서는 `conversation_checkpoint` 429건이 성공했고 현재 요약 427건이 저장돼 있어, 운영 배포 환경에서는 긴 대화 요약도 실제로 사용 중임을 확인했다. 코드 기본값이 꺼짐인 것과 운영 환경값을 혼동하면 안 된다.

## 2. 현재 공개 API

`moly-backend`가 직접 제공하는 영역은 대화, 일기, 건초·광고, 상점·장착, 루틴, 구독 반영, 리뷰·문의, 헬스체크다. 계정(`/me`, 온보딩, 알림 설정, 로그아웃, 탈퇴)은 같은 DB를 쓰는 `moly-auth`가 담당한다.

일기 앱 계약은 다음 세 경로뿐이다.

- `GET /diaries`
- `GET /diaries/{diary_id}`
- `POST /diaries/{diary_id}/read`

사용하지 않던 `GET /v2/diaries*`는 현재 정리 작업에서 라우터·서비스·스키마·OpenAPI까지 제거했다. 반면 상점 `/v2/*`는 `hat`과 `glasses`를 독립 장착하고 v2 전용 상품을 노출하는 실제 계약이므로 유지한다.

앱이 직접 호출하는 `/memory` API는 없다. 장기 기억 검색은 대화 내부에서 자동으로 일어난다.

## 3. 대화와 기억

한 턴은 세 구간으로 처리한다.

1. DB에서 사용자 상태와 프롬프트 재료를 읽고 턴 번호를 예약한다.
2. DB 연결을 놓은 상태로 모델을 호출한다. 필요하면 한 라운드에서 `recall_diaries` 또는 `get_routines`를 호출하고 최종 답을 만든다.
3. 사용자 메시지·캐피 답변·사용량·첫 만남 일기·후속 잡을 한 트랜잭션으로 확정한다.

프롬프트 우선순위는 시스템 페르소나와 안전 규칙이 가장 높다. 그 뒤에 사용자별 대화 약속, 관계 단계, 장기 대화 요약, 최근 대화, 검색된 장기 기억, 현재 상황을 넣는다. DB에 저장된 내용은 참고 자료이며 시스템 규칙을 덮을 수 없다.

장기 기억 저장 흐름:

1. 성공한 대화의 턴 좌표를 `memory_pipeline_states`에 기록한다.
2. `memory_ingest` 잡이 이어진 대화 덩어리에서 사용자 근거가 있는 기억 후보를 추출한다.
3. 본문과 임베딩을 `vecs.moly_memories_v2`에 저장한다.
4. `mem0_memory_registry`가 현재 유효함, 애매함, 중복, 대체됨을 판정한다.
5. 회상 시 벡터 유사도 후보를 받은 뒤 장부 상태와 시간·근거로 다시 거르고 최대 8건을 대화에 넣는다.

`mem0ai`의 자동 기억 관리 정책은 쓰지 않는다. 같은 PostgreSQL의 pgvector 입출력 어댑터만 사용하고, 수명·중복·시간·근거·사용자 경계는 우리 DB 장부가 관리한다.

사용자별로 쉽게 바뀌면 안 되는 말투·호칭·금지사항은 `user_interaction_contracts`와 항목 테이블에 저장한다. 친밀도는 `relationship_events`, `user_relationship_states`, `relationship_profile_renders`로 집계해 프롬프트에 넣는다. 최근 대화 원문이나 벡터 기억만으로 대신하지 않는다.

## 4. 일기와 현재 도구

첫 성공 대화가 확정될 때 `welcome` 일기를 같은 트랜잭션에서 사용자당 한 번 만든다. 가입 시각이나 일기 목록 조회는 생성 계기가 아니다. 일일 일기는 사용자 지역 시각 04:00 배치에서 전날 대화를 바탕으로 만들며, 발행 상태와 `published_at`을 통과한 본인 일기만 API와 대화 도구에 노출한다.

모델에 노출되는 읽기 도구는 정확히 두 개다.

| 도구 | 역할 |
|---|---|
| `recall_diaries` | 자연스러운 일기 언급에서 존재 여부·개수·목록·필요한 전문을 회상 |
| `get_routines` | 특정 날짜의 루틴과 수행 여부 조회 |

registry 밖에 남아 있던 과거 일기 도구 실험 코드는 현재 정리 작업에서 전용 테스트와 함께 삭제했다. 최종 응답 형식을 고정하는 `finish_response`는 두 번째 모델 호출의 내부 계약이지 사용자 데이터 조회 도구가 아니다.

## 5. 비동기 처리와 운영 안전장치

`worker.consumer`가 `async_jobs`를 큐별 고정 동시성으로 처리한다. 결제, 대화 후속, 콘텐츠, 알림, 기억, 유지보수 작업이 서로 슬롯을 빼앗지 않는다. 잡은 처리 권한 기한, heartbeat, 제한 시간, 재시도 간격, 최대 시도 횟수, 중복 방지 키를 갖는다. 죽거나 빈 구간이 생긴 기억 체인은 sweep이 다시 연결한다.

`worker.tick`은 15분마다 사용자 지역 시각을 기준으로 일기·푸시·정리 작업을 예약한다. 출석·루틴·광고 보상 날짜는 00:00 경계이고, 대화 한도·일기 날짜는 04:00 경계라 둘을 합치지 않는다.

헬스체크는 API/DB 준비 상태와 큐별 `ready`·`running`·`dead`, 가장 오래된 잡 나이를 분리해 본다. 잡이 죽으면 Slack에 알리고 복구되면 복구 알림도 보낸다.

## 6. 현재 기본값과 운영 덮어쓰기

코드 기본값 중 중요한 것은 다음과 같다. 실제 배포값은 환경변수와 `app_config`가 우선할 수 있다.

| 설정 | 코드 기본값 |
|---|---:|
| 최근 대화 폴백 | 30개 메시지 |
| 컨텍스트 리셋 | 40개 메시지 또는 30,000자 |
| 리셋 후 유지 | 20개 메시지, 최대 12,000자 |
| 무료/체험/구독 일 한도 | 20,000 / 100,000 / 100,000 |
| 런칭 무료 한도 | 150,000 |
| 런칭 무료 종료 | 2026-09-01 04:00 KST |
| 기억 대화 묶음 | 유휴 180초, 최대 20턴 |
| 기억 잡 동시성 | 소비자당 2 |
| 배치 사용자 동시성 | 1 |
| 아침 일기 푸시 | 꺼짐 |
| 예정시각 dispatcher | 꺼짐 |

운영 `app_config`에서는 런칭 무료 한도 150,000과 종료 시각, 에이전트 100% 적용을 확인했다.

## 7. 남은 운영 과제

- 실제 사용자 대화에 대한 국가·언어별 품질 점검과 회상 정답 세트 확장
- 기억 검색의 상대 거리값과 최소·최대 반환 개수 재평가
- 배치·잡 처리량과 DB pool 대기 시간의 지속 관측 및 근거 기반 동시성 조정
- 아침 일기 푸시와 예정시각 dispatcher는 결과 동일성 검증 후에만 활성화
- iOS에서 언어 변경 화면 및 서버 오류 문구의 다국어 표시 정리

완료된 운영 전환 체크리스트, 일회성 모델 비교 리포트, 구현 계획서는 현재 구조 설명과 섞이지 않도록 저장소에서 제거했다. 적용된 DB 변경의 역사는 `db/migrations/`에 그대로 남긴다.
