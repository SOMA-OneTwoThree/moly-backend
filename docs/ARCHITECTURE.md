## 시스템 경계

```mermaid
flowchart LR
    Client[모바일 앱] --> Auth[moly-auth]
    Client --> API[FastAPI API]
    Auth --> DB[(Supabase PostgreSQL)]
    API --> DB
    API --> LLM[모델 공급자]
    Tick[시간대별 tick] --> DB
    Consumer[상주 consumer] --> DB
    Consumer --> LLM
    Tick --> Push[FCM]
    RC[RevenueCat] --> API
    Ads[광고 SSV] --> API
```

- `moly-backend`: 대화·일기·감정 기록·루틴·경제·상점·구독·광고·운세·트레이닝·배너·BGM.
- `moly-auth`: 계정·온보딩·프로필 변경·알림/기기 설정·로그아웃·계정 삭제 시작.
  두 서버가 공유하는 DB 함수·프로필·삭제 장벽 계약은 함께 유지한다.
- API는 HTTP JSON 요청·응답을 사용한다. FCM은 별도 푸시 채널이며 기기 도착을 보장하지 않는다.
- API, tick, consumer는 같은 저장소의 별도 프로세스다. tick 실행과 consumer 실행을 서로 대체하지 않는다.

소스: [라우터 등록](../app/main.py), [API](../app/api/), [worker](../worker/).

서비스는 권한과 도메인 정책을, DB는 유일성·참조·원자적 상태 변경을 맡는다.

## 공통 규칙과 시간

클라이언트는 DB를 직접 쓰지 않고 서버가 반환한 권한·가격·잔액·한도를 사용한다.
플랜과 체험의 출처는 조회 시 판정하며 서로 다른 출처를 `trial` 하나로 뭉쳐 정책을 정하지 않는다.
건초는 `hay_transactions` 원장과 프로필 잔액을 같은 트랜잭션에서 갱신한다. 광고는 검증된 SSV,
결제는 검증된 공급자 이벤트가 지급 근거다. 클라이언트 완료 콜백으로 지급하지 않는다.

| 기준 | 사용자 현지 경계 | 사용처 |
|---|---|---|
| `activity_date` | 04:00 | 대화 한도·일기 귀속 |
| `reward_date`/달력 날짜 | 00:00 | 출석·루틴·광고 보상·운세·현재 감정/기억 시점 표시 |

00:00~03:59에는 두 날짜가 다를 수 있다. `user_daily_stats.activity_date`라는 컬럼명만 보고
모든 도메인의 날짜를 같게 계산하지 않는다. 감정 기록 API는 요청된 날짜를 그대로 보존한다.
소스: [time_utils.py](../app/core/time_utils.py), [app_day.py](../app/core/app_day.py).

생성 콘텐츠의 지원 언어는 `ko/en/ja`다. 프로필 지역 태그는 기본 언어로 정규화하고 미지원 값은
영어로 폴백한다. API별 명시 언어 입력의 허용 범위는 OpenAPI를 따른다.

## 턴 처리와 발행

```mermaid
flowchart LR
    Request[인증·멱등 키] --> Reserve[사용자 범위 확인·턴 예약]
    Reserve --> Context[컨텍스트 구성]
    Context --> Inference[트랜잭션 밖 모델·도구 호출]
    Inference --> Validate[완결성·언어·참조 검증]
    Validate --> Publish[lease·generation·삭제 장벽 재검사 후 확정]
    Publish --> Jobs[기억·요약 등 후속 작업]
```

1. 인증된 사용자와 삭제 장벽, 요청 해시·멱등 결과를 확인한다. 사용자별 lease(기한이 있는 처리 권한)로 겹치는 턴을 제어한다.
2. 프로필·권한·현재 한도·최근 원문·발행 가능한 요약·현재 상태를 읽고 외부 호출 전에 트랜잭션을 닫는다.
3. 선택된 경로가 모델 응답 또는 제한된 도구 실행을 수행한다. 모델/도구를 기다리는 동안 사용자 락이나
   읽기 트랜잭션을 계속 잡지 않는다. 모델 호출의 사용량 원장은 별도 책임이다.
4. 완결성·출력 언어·참조 대상을 검증한다. 빈 답이나 잘린 출력을 정상 답변으로 발행하지 않는다.
5. 확정 시 사용자 락을 다시 얻고 lease·컨텍스트 revision·기억 generation·삭제 장벽을 재검사한다.
   운세·일기 참조도 현재 소유권/공개 상태를 다시 확인한다.
6. 사용자/캐피 메시지·가중 사용량·멱등 결과·후속 작업을 함께 확정하고 lease를 해제한다.

같은 사용자·같은 멱등 키는 같은 요청을 가리킨다. 다른 본문에 키를 재사용하거나 진행 중인 요청을
새 요청처럼 중복 실행하지 않는다. 과거 응답의 replay도 현재 삭제/참조 공개 계약을 우회하지 않는다.
소스: [chat_turns.py](../app/services/chat_turns.py), [멱등 기록 모델](../app/models/idempotency_key.py),
[privacy.py](../app/services/privacy.py), [chat.py](../app/services/chat.py).

## 입력 컨텍스트와 캐시

| 재료 | 취급 |
|---|---|
| 언어별 성격·출력·정보 사용 규칙 | 코드가 소유하는 정적 system 앞부분 |
| 호칭·대화 약속·관계 사실 | 사용자 범위와 유효 상태를 확인해 제공 |
| 최근 원문·선발화 | 확정된 순서·시각·컨텍스트 경계를 보존 |
| checkpoint 요약 | 발행 상태·포함 범위·기억 generation을 확인한 서버 컨텍스트 |
| 현재 시각·앱 상태·오늘 감정·회상 결과 | 변화하는 컨텍스트로 분리하고 필요한 정보만 제공 |
| 도구 결과·기억·요약 안의 텍스트 | 데이터이며 서버 지시나 권한을 대체하지 않음 |

불변 프롬프트 앞에 매 턴 바뀌는 값을 넣어 캐시를 깨지 않는다. 실제 조립 순서는 `chat._build_system`과
`post_message`를 함께 본다. 저장된 문구의 이름 표시는 `naming.to_placeholder`로 바꾸고 제공 시
`naming.render`로 현재 호칭을 복원한다. 사용자 프로필·원래 발화까지 익명 문자열로 저장된다는 뜻은 아니다.

### 시간과 일시 상태

시간·감정의 사용 조건은 모델에 전달하는 프롬프트 규칙이다. 아래의 DB 조회 범위 제한과 코드 출력 검증과는 구분한다.

현재 시각과 과거 메시지의 시각을 구분한다. 과거 발화의 오늘·어제·지금은 당시 기준이다.
배부름·졸림·이동 등의 일시 상태가 계속되거나 끝났다고 단정하지 않고, 시간이 지난 상태를 새로운
질문·조언의 전제로 선제 재사용하지 않는다. 자정만으로 바로 이어지는 화제를 끊지도 않는다.

소스: [turn_context.py](../app/services/turn_context.py), [time_utils.py](../app/core/time_utils.py),
[mem0_recall.py](../app/services/mem0_recall.py).

### 사용자 감정 선택의 정보 권한

- `mood_context.today_block`은 사용자 현지 오늘 날짜의 `kind`만 조회한다. `note`와 과거 날짜는 읽지 않는다.
- 대화에 허용되는 값은 `annoyed/tired/neutral/content/excited`이며 언어별 선택명으로 전달한다.
  다른 값·누락·조회 실패는 `unknown`이다. 기록 API 자체의 허용 값과 대화의 5종 allowlist는 별개다.
- 사용자가 **오늘 앱에서 고른 감정 이름을 명시적으로 물을 때만** 전달된 선택명을 답할 수 있다.
  일반적인 기분 질문·피곤하다는 말에는 노출하지 않고 말투·화제·질문 결정에도 사용하지 않는다.
- 현재 발화를 우선한다. 과거 대화에서 들은 선택명을 오늘 값으로 복원하지 않는다.
  `unknown`은 모른다는 뜻이지 기록이 없다는 증거가 아니다. 앱 메모·과거 선택을 아는 것처럼 답하거나
  캐피 일기 조회로 대신하지 않는다.

소스: [mood_context.py](../app/services/mood_context.py), [언어별 정보 권한](../app/services/prompts.py).

## 모델과 도구

[agent/runtime.py](../app/services/agent/runtime.py)는 등록 도구·호출 횟수·동시성·결과 예산·절대 마감을 제한한다.
현재 경로를 항상 별도의 계획 모델과 발화 모델 두 호출로 설명하지 않는다. 코드가 선택한 단발/도구
경로와 실제 호출 내역을 기준으로 확인한다.

도구에는 서버의 `ToolContext.user_id`를 주입한다. 모델은 사용자 ID·SQL·임의 권한 필터를 지정할 수 없다.
조회 기간·행 수·문자 수와 턴 합계 결과 예산을 제한하고, 잘린 결과는 완전한 목록으로 취급하지 않는다.
현재 조회 도구는 일기·루틴이며 기억 회상은 별도의 컨텍스트 경로다.
[registry](../app/services/agent/tools/registry.py)의 제어 도구 목록은 비어 있고 대화형 망각은 제공하지 않는다.
모델이 도구를 골랐다는 이유만으로 DB 변경 권한이 생기지 않는다.

[llm.py](../app/services/llm.py)는 남은 foreground 마감 안에서 요청과 허용된 재시도를 제어한다.
SDK의 숨은 재시도와 애플리케이션 재시도를 겹쳐 전체 마감을 넘기지 않는다. 실패 시 무조건 다시 호출하지
않으며 취소/실패 원장을 정리한다. 확정되지 않은 실제 공급자 비용은 `unknown_usage`로 남을 수 있다.

트레이닝 주관식 채점은 같은 `llm.py`로 `model_training_grade`를 부른다. 10초 foreground 마감을 주고 DB
트랜잭션 밖에서 호출한 뒤, 잠금을 다시 잡고 단계·기회를 재확인해 저장한다. 실패·마감 초과·형식 오류는
통과로 처리하고 원장에는 `training_grade` 용도로 남긴다. 계정을 알아볼 정보는 프롬프트에 넣지 않는다.

### 출력 방어

- 프로필의 지원 언어로 답하고, locale의 정상 문자·허용 Latin 이름·사용자 닉네임을 보존한다.
- 허용되지 않은 외국 문자 계열은 실제 코드로 제거한다. 따옴표 안이라는 이유로 필터를 면제하지 않는다.
- 제거 결과가 의미 문자 없는 부호만 남으면 빈 답으로 처리한다. 미완성·빈 답은 `AI_UNAVAILABLE`로
  종료하며 정상 답변처럼 발행하지 않는다.
- 채팅의 줄바꿈·인용·의미 있는 대시는 보존한다. 단어를 보고 평서문에 물음표를 임의 삽입하지 않는다.
  채팅 정제 옵션을 일기 공용 정제의 기본 동작과 혼동하지 않는다.

소스: [text_clean.py](../app/services/text_clean.py), `chat._clean_reply`, `llm.require_completed_text`.
이 방어가 자연스러움이나 모든 내용 안전성을 보장하는 것은 아니다.

### 위기 대화 분기

새 경로는 전역 `crisis_guard_enabled`와 `crisis_guard_policy_version=crisis-v2`가 맞으면
전체 사용자에게 적용한다. 사용자 목록이나 비율로 적용 대상을 나누지 않는다. 현재 말과 발행된 직전
최대 6개 메시지를 OpenAI Decisions API에 한 번 보낸다. 본인의 현재 생각, 실행 의도·계획,
준비·행동, 말뜻 불명확, 해당 없음으로 구분한다. 확률은 위기 정도가 아니며 구형 0.4 기준을 쓰지 않는다.
현재 구현은 기억 조회가 필요 없는 요청도 판정부터 마친 뒤 일반 응답을 시작한다. 판정의 2초 마감
초과·장애는 일반 답변으로 진행하며 정상 판정과 구분해 기록한다. 일반 기억 조회·입력 예산·운세
오류가 고정 응답을 막지 않도록 발행 경로를 분리한다.

생각과 말뜻 불명확에는 같은 고정 질문을 보낸다. 한국어는 “어떤 뜻인지 조금만 더 얘기해줄래?”,
영어는 “Can you tell me a little more about what you mean?”, 일본어는
“どういう意味か、もう少し教えてくれる？”이다. 방법·양 요청의 고정 거절 접두사는 유지한다.
2026-11-03 사용자 지시로 상황 질문과 뜻 질문을 나누던 문구 정책을 통일했다. 분류 선택지·판정
확률·분기는 바꾸지 않았으며 과거 문구 선택 불일치의 평가 기록을 새 성과로 재분류하지 않는다.
최신 캐피 재질문이 최근
6개 안에 있으면 같은 우려를 진지하게 확인한 답에만 안내한다. 최신 개입이 안내면 생각 수준의
반복에는 다시 묻지 않는다. 새 실행 의도·계획·준비·행동은 항상 안내한다. 화제가 바뀌면 따라간다.
재질문도 안내도 모델이 생성하지 않는다. 안내는 의료 서비스가 아니고 진단·치료를 제공하지
않는다는 설명과 전문 상담기관에 연락하라는 안내만 담는다. 응급 안내·전화번호·링크·국가 분기는 없다.
고정 응답에는 모델 문장이나 카드·운세·주제 제안을 붙이지 않는다. 두 경로는 한도 소진 때도
0차감으로 보낸다. 재질문과 안내 턴은 사용자와
캐피 양쪽을 `safety_check`·`safety`로 저장한다. 판정용 최근 6개에는 종류와 관계없이 원문을 유지한다.
유효한 일반 대화 판정 뒤에는 일반 답변 입력에서 과거의 두 종류 메시지만 제외한다. DB 원문·현재
입력·일반 대화·필수 기억·도구 결과는 유지하고, 제외한 메시지를 선발화 system 블록으로 옮기지도
않는다. 기술적 판정 실패에는 기존 최근 원문으로 기본 모델이 답하는 경로를 유지한다.
두 종류는 일기·장기 기억·대화 약속·관계 기록·요약 입력에서도 제외한다. 판정 비용은 회사 사용량
원장에 따로 기록한다.

정상 판정으로 일반 대화에 돌아왔고 최근 재질문·안내가 남아 있으면, 현재 주제를 따르고 앞의
무거운 이야기를 먼저 다시 꺼내지 않는 지시를 그 답의 휘발 입력에만 추가한다. 판정 결과·이유는
전달하지 않는다. 일반 대화 맥락과 현재 사용자의 직접적인 상담 연락처 질문은 계속 다룰 수 있다.
일반 모델은 제외한 과거 위기 턴의 세부사항을 회상하지 못하므로, 뜻이 불분명한 참조에는 필요한
뜻을 물을 수 있다. 이 입력 분리는 기존 구형 요약에 남아 있는 위기 내용까지 정리하는 작업이 아니며,
사용자별 전환 전 파생 정보 검증은 계속 필요하다.

소스: [crisis_guard.py](../app/services/crisis_guard.py), [crisis_chat.py](../app/services/crisis_chat.py).

## 원문 연속성과 요약

원문은 [messages](ERD.md#대화와-컨텍스트)가 기준이다. 최근 구간은 서버 상한 안에서 보존하고,
checkpoint의 실제 coverage와 남은 원문을 연결한다. 발행되지 않은 요약이나 다른 사용자·generation의
요약을 넣거나, 요약이 생겼다는 이유만으로 그 뒤 원문을 누락시키지 않는다. 상한·트리거는 설정과
[checkpoint_repo.py](../app/services/checkpoint_repo.py), [checkpoint.py](../app/services/checkpoint.py)를 따른다.

요약은 원문을 대체한 새 사실이 아니라 파생 데이터다. 재추출·삭제·발행 경쟁에서는 generation과
privacy epoch를 확인해 오래된 작업이 새 컨텍스트를 덮어쓰지 못하게 한다.

새 보존 경로는 `context_retention_v2_enabled`와 사용자별 전환 확인을 따로 검사한다. 새 작업은
기능을 끄면 게시하지 않으며, 이미 현재 세대의 v5 상태를 게시한 사용자의 읽기는 구형 요약으로
돌아가지 않는다. v5는 현재 주제·미해결 질문 등의 변경 목록만 적용하고 모델 출력에 없는 기존
항목은 유지한다. 종료된 항목은 게시 이력에 보존하고 이후 현재 입력에서는 제외한다.

일반 원문은 사실 처리·대화 약속 처리·검증된 v5 게시가 끝난 범위만 입력에서 제외한다. 처리 전
원문이 입력 예산을 넘으면 짧은 뒷부분으로 대체하지 않고 답변을 보류한다. 배경 작업도 전체 입력
예산을 검사하며 큰 구간과 긴 메시지는 UTF-8 경계를 보존해 여러 작업으로 처리한다. 중간 결과는
게시하지 않고 진행 위치를 저장한다. 기능을 다시 켜면 추가 발화 없이도 기존 진행에서 재개한다.
신규 일반 요약은 `packed-v1`을 사용한다. 2,048바이트 원자 조각의 검증 계획은 유지하되,
실제 이전 상태·JSON·시스템 문구·출력 예약 2,000토큰을 합쳐 16,384 상한에 들어가는 연속
조각을 한 번에 처리한다. 같은 메시지의 인접 조각은 본문 순서·절대 UTF-8 위치·전체 해시를
확인해 합친다. 진행 위치는 호출 횟수가 아니라 완료한 원자 수다. 호출 전 상태로 같은 묶음을
다시 계산하고, 전후 상태 해시·원문 범위·버전을 검사한 뒤 진행을 저장한다. 마지막 원자까지
완료해야 상태 순서를 한 번 올린다. 기존 부분 작업·완성 초안·정기 재검증은 기존 방식으로
재개하며, 새 버전으로 재해석하지 않는다. 사용자별 기존 예약·게시 동시성도 유지한다.
진행 중인 대상의 명시적 이름 변경은 현재 지칭의 연결을 보존한다. 묶음 전용 시스템 문구의
해시도 계획에 포함하므로, 문구가 달라진 기존 묶음 진행·완성 초안은 원문을 유지하고 중단한다.
확대 묶음의 출력이 잘리면 그 결과를 적용하지 않고 동일 시작 상태에서 원자 한 개씩 처리한다.
남은 실패 예산은 실제 모델 호출 직전에 저장하므로, 기능을 끄고 켜거나 작업 행이 바뀌어도
늘어나지 않는다. 입력 상한에 못 들어가 모델을 호출하지 않았다면 예산을 쓰지 않는다.
미처리 원문이 4,096 보수 단위에 닿으면 이번에 저장한 양쪽 메시지까지 포함한 작은 범위를 고정해
선행 작업을 시작한다. 사실 추출·선호 정리와 비공개 요약 계산은 겹쳐 실행하고, 마지막 게시만
사실·선호 완료를 기다린다. retention 선호 작업은 기억 큐를 사용하며 실패 예산은 3회다.
요약 조각 내부 순서는 유지한다. 완성 초안은 전체 조각 목록·진행 위치·해시·부모와 함께 저장하고,
게시 전용 작업은 모델을 부르지 않고 현재 원문·개인정보 epoch·세대·근거를 다시 검증한다.
완료 확인이 다시 대기로 바뀌어도 같은 초안을 보존한다. 개인정보 상태가 바뀐 작업은 폐기한다.
기능을 끄면 새 모델 호출·후속 예약·공개 게시를 중단한다. 끄기 전에 이미 계산한 완성 초안은
현재 원문·세대·개인정보 상태를 검증한 뒤 원래 작업의 비공개 payload에만 보관할 수 있다.
다시 켰을 때 이 완료본은 모델을 다시 부르지 않고 게시 검증부터 재개한다.
검증된 게시 후에도 기존 처리 목표가 남으면 후속 한 건을 예약한다. 사용자 잠금이 바쁘거나 선택적
예약에 실패하면 현재 게시를 되돌리지 않고, 저장된 목표를 정기 점검에서 이어 처리한다.

일찍 게시한 요약이 최근 대화 원문까지 없애지 않도록 약 2,048 보수 단위의 완결 대화도 함께 읽는다.
요약 예약량은 미처리 원문만 계산하고, 실제 응답 입력은 두 범위를 중복 없이 합쳐 검사한다.
입력 상한을 넘으면 검증된 요약에 이미 포함된 앞부분만 생략할 수 있다. 현재 질문·미처리 원문·
필수 사실·선호·도구 결과는 이 과정에서 제거하지 않는다. 도구 결과가 추가된 뒤에도 같은 경계를 지킨다.
생략 가능 여부는 배열 위치나 같은 문구가 아니라 사용자·메시지 ID·세대·원문 해시로 확인한다.
검증된 v5와 선행 처리 완료 범위에 속한 실제 조회 원문만 생략하며, 날짜·이름 표기와 도구 호출
변환 뒤에도 이 식별 정보를 유지한다. 식별 정보는 모델에 보내지 않는다. 전환 완료 사용자의
읽기에는 구형 위기 대화 압축을 적용하지 않으며, 위기 기능 설정을 꺼도 이 규칙은 유지한다.
같은 근거 문구가 여러 번 나오면 모델이 제공된 조각 안에서 몇 번째 표현인지 명시한다. 서버가
실제 문자열과 회차를 확인해 기존 절대 UTF-8 위치·전체 원문 해시로 저장한다. 중복인데 회차가
없거나 범위가 틀리면 계속 거부하며, 서버가 임의로 첫 번째 위치를 선택하지 않는다.

대화의 전체 입력과 원문 읽기 보호 상한은 32,768의 보수 단위를 쓴다. 이 값은 UTF-8 바이트와
예약분으로 계산하며 모델의 실제 토큰 수나 컨텍스트 한도가 아니다. 도구 실행 지침·응답 형식까지
포함해 검사하고, 후속 도구 결과나 길이 복구 지시가 추가된 뒤에도 다시 검사한다. 배경 작업과
정정 입력의 기존 16,384 제한은 별도다. 현재 질문·필수 기억·계약만으로 상한을 넘으면 과거 원문을
정리해도 해결되지 않으므로 같은 정리 작업을 반복 예약하지 않는다. 무제한으로 쌓인 계약이
항상 들어간다는 보장은 없다.

새 선호 정리는 기존 문서와 JSON 직렬화·출력 예약분까지 포함한 같은 배경 입력 상한 안에서
완전한 메시지를 함께 처리한다. 첫 메시지만으로 넘치면 UTF-8 경계를 지켜 나누며, 구형 경로의
2,048바이트 분할과 출력 2,000토큰 상한은 유지한다.
확대 처리의 출력이 길이 상한에서 잘리면 해당 출력은 해석·저장하지 않는다. 현재 원문과 기존
문서가 그대로인지 확인한 뒤 남은 실패 예산으로 2,048바이트 분할 작업을 예약한다. 이후 조각도
같은 분할 방식과 남은 실패 예산을 이어받으며, 다시 잘리면 기존 재시도 규칙을 적용한다.

저장 완료 대화의 선제 정리가 필요하거나 입력이 넘치면 `retention_pressure_through_message_id`에 처리할 마지막
완결 답변을 기록하고, 최근 한 턴도 바로 정리 작업에 포함한다. 실행 중 작업의 원문 범위는 바꾸지
않는다. 검증된 게시가 현재 목표를 덮었을 때만 목표를 해제하며, 세대·개인정보 상태가 바뀌면
목표를 무효화한다. 예약 순회는 UUID 위치를 저장해 앞쪽 사용자에게만 계속 머무르지 않는다.
새 요약을 예약할 때 같은 범위에 필요한 선호 작업을 예약하고 최초 기억 작업의 기본 대기만 앞당긴다.
현재 세대·개인정보 상태·정확한 작업을 확인하며, 생산자의 같은 커밋 또는 요약 확정 잠금 밖의 짧은
트랜잭션에서 실행한다. 실패 재시도 간격과
횟수·실행 중인 작업은 바꾸지 않는다. 추가 발화 없이도 필요한 선행 처리를 시작할 수 있다.
진행 중인 요약의 범위는 고정하고, 더 큰 처리 목표가 저장되면 그 목표의 최초 기억 작업도 바로
확인한다. 기억 처리 연결이 실제로 빠진 경우에는 현재 커서의 원래 중복 방지 키로만 예약한다.
기존 대기·실행 작업이나 같은 커서·재처리 세대의 종료 작업이 있으면 새 실패 예산을 주지 않는다.
기억·선호·요약 작업의 처리 시도 뒤에는 별도 짧은 트랜잭션으로 게시 대기를 확인한다. 선행 처리가
실제로 완료된 현재 세대의 게시 작업만 실행 시각을 앞당긴다. 실제 오류의 재시도 간격은 유지한다.
알림 자체를 커밋 성공으로 간주하지 않으며, 알림 실패 시 기존 예약 시각이 대체 경로로 남는다.
게시 대기의 확인 간격은 처리 횟수 기준으로 120회까지 5초, 170회까지 60초, 그 뒤 5분이며 포기하지 않는다.

선호 작업(`contract_compile`)은 마지막 시도의 내용 실패(형식 오류·빈 응답·길이 초과·근거 불일치·병합
오류·문서 2KB 초과)를 dead로 끝내지 않는다. 모델 후보를 버리고 커서를 넘기며, 버린 이유와 개수는
`result_detail`에 남긴다. 선호·요약 작업이 일시 장애(분류되지 않은 예외·시간 초과·처리 권한 만료 등)로
dead가 되면 같은 범위의 중복 방지 키가 막혀 처리가 멈추므로, 새 행으로 다시 만든다. 요약은 형식 검사
실패(`summary_invalid`)도 포함한다. 간격은 30분에서 시작해 다시 만들 때마다 두 배, 최대 24시간이다.
dead 행은 그대로 두고 payload는 지금 기준으로 새로 만들며, 같은 dead마다 한 건만 생긴다. 선호 작업은
선호 처리를 예약하는 곳(대화 턴·요약 게시 대기 등)에서, 요약 작업은 예약 순회(memory sweep)에서 다시 만든다.

대화 입력을 준비하다 원문 정리가 필요하면 같은 HTTP 요청과 처리 권한을 유지한 채 DB 연결과
잠금을 반환하고 예약 응답에 받은 고정 목표의 게시를 기다린다. 중간 범위의 게시만으로 재개하지
않고 검증된 범위가 그 목표까지 도달하면 정상 입력 준비를 한 번만 다시 한다. 대기 중 새 목표를 따라 늘리지 않는다.
판정과 질문 임베딩 호출은 반복하지 않고, 기억·선호·유효성은 새로 확인한다. 설정·개인정보 상태·
세대·직전 원문·날짜·시간대가 바뀌면 응답을 저장하지 않는다. 저장과 차감은 최종 한 번이다.
일반 대화의 기존 8초 기준은 유지한다. 이 정리 대기가 발생한 요청만 최초 요청 시작부터 최대
12초를 공유하며, 대기·다시 준비·모델 생성·저장을 포함한다. 도구 실행 뒤에는 재준비하지 않는다.
대기는 다시 준비할 시간(약 1.5초)을 남기고 멈춘다. 게시가 그 안에 오지 않거나, 기다릴 수 없거나,
같은 사용자의 대기 중 요약 작업이 이미 60초 넘게 밀려 있으면 503 대신 같은 처리 권한으로 한 번만
줄인 최근 기록을 준비해 답한다. 저장된 원문(가장 오래된 것부터)만 빼고, 맨 앞에 남는 캐피 답변도 뺀다.
페르소나·휘발 블록·요약·기억·확인된 사실과 현재 입력은 유지하고 "앞 대화가 빠졌을 수 있다" 안내를
붙인다. 도구 호출 뒤 초과를 줄이려 출력 여유 8,192를 먼저 노린다. 앵커와 요약 범위는 바꾸지 않고,
요약 예약은 커밋된 채 남으며 이 턴까지 다시 예약해 게시되면 다음 턴부터 정상으로 돌아온다.
위기 판정이 기술적으로 실패한 요청, 줄여도 들어가지 않는 입력, 도구 호출 뒤 초과는 지금처럼 503이다.
API와 소비자의 완료 알림은 프로세스 사이에 전달되지 않는다. 최초 작업이 유휴 조회의 8초 대기를
받지 않도록 memory/content 두 큐의 빈 조회 대기만 최대 1초로 제한한다. 슬롯이 찼거나 작업이 실제로
실패한 경우의 대기는 유지한다. 기본 설정에서 조용히 빈 큐를 확인하는 횟수는 소비자 하나당 두 큐 합계
초당 약 2회이며, 소비자 수에 비례한다. 기존 완료 알림에 의한 추가 조회는 별도다.
실제 실패로 재시도 횟수를 다 쓴 작업은 자동으로 새 작업을 만들어 반복하지 않는다. 목표와 원문을
보존하고 점검 대상으로 센다. 기능 중단·원문 변경 등으로 게시하지 못한 성공 작업의 진행 재개와는 구분한다.

소스: [context_retention.py](../app/services/context_retention.py),
[worker/checkpoint_jobs.py](../worker/checkpoint_jobs.py), [worker/memory_sweep_jobs.py](../worker/memory_sweep_jobs.py).

## 장기 기억과 사용자별 상태

| 단계 | 책임 |
|---|---|
| 턴 등록 | `memory_pipeline`이 순서·source/ingest/consolidation 진행 위치를 기록 |
| 추출 | 사용자 발화의 근거를 붙인 후보와 후보별 source 저장 |
| 통합 | 중복·대체·모순을 반영해 registry의 유효 상태 결정 |
| 벡터 저장/삭제 | 공급자 상태와 registry를 연결하고 실패한 삭제는 후속 처리 |
| 회상 | 사용자 범위와 registry 상태로 필터한 결과만 대화에 제공 |

벡터 검색 결과만으로 현재 사실을 판정하지 않는다. provider 삭제가 지연돼도 registry에서 배제된 기억은
회상에서 제외한다. `ambiguous`는 없다는 뜻이 아니며 불확실성을 보존한다. 오래된 기억보다 현재 발화가
우선이고, 서버가 직접 소유하는 장착/루틴 상태는 조회된 서버 값과 구분한다.

기억 행은 메시지별 출처·source_turn_seq·revision을 가지며, 다른 사용자의 근거와 연결하지 않는다.
재처리 세대는 `memory_pipeline_states.repair_generation`, 요약 발행 세대는 `chat_contexts.memory_generation`으로 검사한다. 회상 실패는
대화의 보조 정보 실패로 다루고 모른다는 사실을 숨기거나 기억을 지어내지 않는다.
사용자별 대화 약속과 관계 상태는 별도 구조화 상태이며 임의의 자유 서술 하나로 덮어쓰지 않는다.
소스: [memory_pipeline.py](../app/services/memory_pipeline.py), [mem0_recall.py](../app/services/mem0_recall.py),
[worker/mem0_jobs.py](../worker/mem0_jobs.py), [contract_repo.py](../app/services/contract_repo.py).

새 보존 경로의 사실은 `canonical_text`와 원문 근거로 검증하며 `context_priority=required`는
벡터 검색과 별도로 항상 읽는다. 관련 회상은 실제 입력에 제공한 기억의 식별자·본문·활성 상태·
제공자·출처와 표시 시점을 요청 안에서 고정하고, 저장 직전에 같은 자료를 다시 검증한다.
정리용 revision만 달라진 경우는 허용하며, 같은 문구라도 다른 기억이나 다른 원출처로 교체하지 않는다.
원래 출처의 전체 원문과 인용 구간, 작성자·권한·메시지 종류가 바뀌거나 기억이 삭제·퇴역하면 저장하지 않는다.
검증은 원문 → 기억 행 → 출처 순으로 잠그며, 성공한 잠금은 대화 저장의 커밋까지 유지한다.
새 출처 연결로 잠금 대상이 달라지면 전체 잠금을 되돌려 최대 두 번 확인한다. 잠금 대기는 최대
250ms, 이 검증 전체는 남은 요청 시간과 1초 중 작은 값으로 제한한다. 경합 실패는 부분 저장 없이
기존 재시도 응답으로 처리한다. 최초 회상에는 잠금을 잡지 않으며 실패·취소한 회상의 증명은 버린다.
필수 사실과 대화 선호의 기존 변경 검사는 유지한다. 구현은 [provided_memory.py](../app/services/provided_memory.py)에 둔다.
정정이 처리 중이면 이전 파생 정보를 답변에 넣지 않으며 사실·약속·v5 진행 위치가 모두 해당
구간을 처리한 뒤 다시 읽는다. 이 즉시 보류의 정정 탐지는 명시적 표현에 대한 보조 조건이며
모든 자연어 정정을 완전히 판정한다는 뜻은 아니다.

대화 약속의 기간은 현재 대화·하루·지속으로 구분한다. 현재 대화 약속은 요약 경계나 자정 때문에
없애지 않고 사용자 원문의 명시적 종료 근거로 끝낸다. 현재 입력에 종료 표현이 있으면 처리 완료
전에도 해당 대화 약속만 주입하지 않는다. 일반 사실이나 다른 기간의 약속까지 함께 지우지 않는다.

## 일기 참조·기억 관리·계정 삭제

캐피가 쓴 공개 일기와 사용자의 감정 메모를 분리한다. 대화 안의 일기 카드는 서버가 소유권·현재
공개 상태를 재검증한 본문이며 모델이 만든 요약을 원문으로 표시하지 않는다.
`X-Moly-Capabilities: diary-reference-v1`을 보낸 클라이언트만 확장 계약을 사용하고, 카드를 제공한
것만으로 읽음 처리하지 않는다. 삭제·비공개 대상은 본문 없는 `unavailable`로 내린다.

관리 경로의 기억 삭제·재추출은 의미 상태·근거·provider 삭제·진행 위치를 함께 다룬다. 계정 삭제는 `moly-auth`의
`begin_subject_deletion` 장벽에서 시작한다. 메시지·일기·요약·벡터·참조·잡 payload·멱등 응답 사본까지
추적하며, 단순 프로필 CASCADE만으로 외부 저장소 삭제 완료를 선언하지 않는다.
소스: [privacy.py](../app/services/privacy.py), [privacy_jobs.py](../worker/privacy_jobs.py),
[chat_references.py](../app/services/chat_references.py), [DDL](../db/schema.sql).

## 사용량과 운영

사용자 한도는 실제 호출 내역을 바탕으로 한 **가중 토큰**이고 실제 USD 원가는
`ai_usage_ledger`·유효시점별 `ai_price_catalog`의 별도 계산이다. 실패/미확인 원가를 0으로 만들지 않는다.
일기 발행의 대화량 조건은 사용자 문자수이며 한도 토큰과 같은 단위가 아니다.

배포/롤백·원장 점검은 [운영](OPERATIONS.md)을 따른다. 기능 플래그·모델·지연 한도는 코드 기본값과
환경별 실제 설정을 구분한다. 특정 운영값이나 대화 품질 개선 실적을 이 문서에서 선언하지 않는다.

## 비동기 작업과 데이터

- tick은 사용자 시간대에 맞춰 일기·알림 등의 작업을 수행/예약한다. 실행 주기·실제 호스트 역할은
  배포 설정으로 확인하며 코드 기본값으로 운영 활성 상태를 추정하지 않는다.
- consumer는 `async_jobs`의 lease로 작업을 선점하고 완료·재시도·회수한다. 기억, 요약, 일기 회상,
  관계·삭제 후속 처리 등은 등록된 handler가 담당한다.
- 완료 작업의 payload와 멱등 응답 사본은 도메인 원본과 별도 보존·비식별화 정책을 적용한다.
- 큐의 미해결 오류는 `jobs._STATS_SQL`로 판단한다. 성공 replay의 모든 조상을 제외하며 raw dead
  행 수를 현재 장애로 세지 않는다.

소스: [tick](../worker/tick.py), [consumer](../worker/consumer.py), [jobs](../app/services/jobs.py).
테이블 관계는 [ERD](ERD.md)를 따른다.

## 보안과 변경 관리

- 일반 API는 Supabase JWT를 JWKS로 검증한다. 공개 health·설치 귀속·서버 간 웹훅은 각자의 계약을 쓴다.
- 사용자 범위는 인증된 ID로 제한한다. 도구 인자에 사용자 ID·SQL·임의 필터를 허용하지 않는다.
- 도메인 테이블은 RLS와 객체 권한으로 클라이언트 직접 접근을 막는다. 서버 역할의 우회 권한은
  서비스의 소유권 검사·삭제 장벽을 대신하지 않는다.
- 계정 삭제는 `moly-auth`의 장벽 설정으로 시작하며 API·잡 발행에서도 재확인한다. 계정 삭제 후에도
  남겨야 하는 최소 삭제 장벽과 감사 정보는 사용자 콘텐츠와 별도로 취급한다.
- 모델의 출력·도구 결과·저장된 기억은 신뢰된 명령이 아니다. 문자 정제만으로 보안을 보장하지 않는다.
- 키·JWT·연결 문자열·개인 본문을 로그·문서·CI 출력에 넣지 않는다. 개발/운영의 역할·대상·이미지 경계를 유지한다.

DB 적용과 코드 배포는 별개다. 기존 DB에 baseline을 다시 실행하지 않으며, 혼합 버전의 reader/writer
호환과 데이터 보존을 확인한 후 변경한다. [DB 안내](../db/README.md)와 [운영](OPERATIONS.md)을 따른다.
