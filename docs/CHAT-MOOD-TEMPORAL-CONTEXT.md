# 감정 일기와 대화 시간 정보

## 동작과 범위

오늘의 사용자 감정 일기를 매 턴 다시 읽어 감정과 메모를 대화에 제공한다. 수정·삭제도 다음 턴에 반영된다. 사용자 시간대의 달력 날짜(00:00)를 사용하며, 토큰·일기 생성에 사용하는 활동일(04:00)은 그대로 둔다.

- 오늘 기록이 없으면 어제 기록으로 대체하지 않는다. 조회 실패와 기록 없음도 구분한다.
- 과거 기록은 `get_mood_entries`로 필요할 때만 읽는다. 캐피가 쓴 일기 조회와 구분한다.
- 상대 날짜 또는 명시한 날짜 범위로 최대 31일을 조회한다. 기본 반환은 최근 3건, 최대 5건이다. 전체 일치 개수와 실제 반환 개수, 추가 기록 여부를 함께 전달한다.
- 기록 날짜·작성 시각·사건 시각을 구분한다. 현재 사용자가 말하는 상태가 기록보다 우선한다.
- 과거 발화에는 고정된 절대 시각을 붙이고, 현재 시각과 마지막 턴으로부터의 경과 분을 별도로 제공한다. 배부름·졸림·이동 중 같은 일시 상태를 오래 뒤의 답변 근거로 재사용하지 않도록 안내한다. 상태가 끝났다고 단정하거나 임의의 수명으로 기록을 삭제하지 않는다.
- 부상이나 지난 사건의 안부, 자정 직후 이어지는 대화는 허용한다. 과거 선발화를 방금 건넨 인사로 표시하지 않는다.
- 회상 기억의 근거 발화 시각은 ‘언급’으로 표시한다. 기억 행이 DB에 들어온 시각을 사건 시각으로 사용하지 않는다.

## 컨텍스트와 캐시

배치는 `고정 프롬프트 → 고정 시각이 붙은 과거 대화 → 현재 시각·감정 일기 등 휘발 system 블록 → 현재 사용자 발화`다. 경과 시간을 과거 메시지마다 갱신하지 않는다. 같은 분의 연속 메시지는 시각 표식을 공유한다.

| 항목 | 상한·측정 |
| --- | --- |
| 오늘 감정 일기 | 감정 40자, 메모 400자. DB 조회 단계에서 길이 제한 |
| 과거 감정 일기 | 각 메모 200자. 기존 전체 도구 결과 예산 600토큰 안에서 이 도구는 최대 480 추정 토큰 |
| 결과 축약 | 메모를 먼저 줄인 후 오래된 항목을 제외. 날짜와 개수는 자르지 않음 |
| 매 턴 추가 블록 | 기록 없을 때 약 103, 최대 길이 예시 약 541 추정 토큰(시각 안내 포함) |
| 고정 프롬프트 증가 | ko/en/ja 약 313/233/323 추정 토큰. 도구 스키마 약 297 추정 토큰 |

추정치는 기존 런타임의 보수적인 문자 기반 계산이다. 실제 토크나이저 수치와 다르다. 과거 시각 표식은 메시지 수에 따라 별도로 증가하며 기존 40개 메시지 리셋·20개 보존 정책을 유지한다. 감정 기록을 채팅 메시지나 장기 기억으로 복제하지 않는다.

## 검증 (2026-09-15)

- `ruff check app worker scripts tests db`: 통과.
- `pytest -q --ignore=tests/integration`: **2,457개 통과**. 기존 Starlette 경고 1개.
- `MOLY_MOOD_TEST_ENV=dev pytest -q tests/integration/test_chat_mood_context.py`: **5개 통과**. 허용된 개발 Supabase에서 임시 사용자·기록으로 사용자 격리, 수정·삭제, 날짜 범위, 길이 상한, 조회 실패 후 트랜잭션 복구 검증. 모든 fixture를 롤백하고 사용자 잔존 0건 확인.
- 배너·자산 검사, 운세 생성 문서 및 콘텐츠 구조 검사 통과. 스키마 변경은 없다. CI의 기존 스키마 재구성 작업은 로컬에서 재현하지 않았다.
- 기존 개발 API `/health`: development/ok. 이 브랜치의 코드는 아직 배포하지 않았다.
- 실제 `gpt-5.6-luna`, `reasoning_effort=none`: 한국어·영어·일본어 24개 합성 사례의 변경 전후 48회와 핵심 사례 반복 12회. 호출 오류 0건. 오늘 감정 정보 사용, 현재 발화 우선, 메모 안 지시 무시를 확인했다.
- 실제 agent runtime + 도구 스키마로 핵심 10개 사례를 2회씩 추가 확인했다. 식사 관련 8개 응답에서 지난 배부름을 재사용하지 않았고, 부상 안부 6개와 자정 직후 연결 2개를 유지했다. 나머지는 감정 변경·메모 안 지시 무시였다. 추가 도구 호출 없이 1.1–2.1초 범위였다.
- 실제 runtime과 개발 DB의 읽기 전용 연결로 조회 질문 6개 검증: ko/en/ja 어제 감정 일기, 명시한 주간 범위, 캐피 일기, 루틴 모두 해당 도구로 정상 조회했다. 빈 날짜를 다른 날짜로 대체하지 않았다. 유효한 데이터 내용·부분 반환은 위 DB 통합 테스트에서 검증했다.
- 개발 DB의 오늘 기록 읽기 15회: 중앙값 66.9ms, 최대 159.9ms. 짧은 실제 기록 블록은 약 42 추정 토큰이었다.
- 실제 프롬프트와 32개 고정 과거 메시지를 둔 4회 호출에서 시각·감정 값을 바꿔도 `cache_read_tokens > 0`을 확인했다. 단위 테스트에서도 과거 프리픽스의 바이트가 유지됨을 검증했다. 캐시 적중률 자체는 provider 상태에 따라 달라진다.
- 별도 검토 에이전트의 최종 코드 리뷰에서 추가 필수 수정 사항 없음.

모델 문구를 완전히 보장하는 검증은 아니다. 넓은 비교 사례에서 날짜만 알려진 면접이 이미 끝났다고 추측한 응답도 1회 있었다. 일반 사건의 완료 여부 추론은 개발 환경에서 추가로 관찰해야 한다. 이번 변경의 핵심인 오래된 일시 상태 재사용과 정상 안부 보존은 위 반복 사례로 확인했다.

## 개발 배포와 요약 버전

DB 마이그레이션과 운영 DB 변경은 없다. 현재 시각·오늘 감정 일기·과거 조회는 코드 배포로 적용된다. 과거 요약에 시각을 보존하는 v4 생산은 별도 플래그로 기본 비활성화한다. 새 소비자는 기존 v3와 v4를 각각의 해시·프롬프트로 처리한다.

백엔드와 워커가 순차 교체되므로 **모든 개발 checkpoint 소비자가 새 버전임을 확인한 뒤** 아래 설정을 개발 DB에만 적용할 수 있다. 이 PR 작업에서는 실행하지 않았다. `context_checkpoint_enabled`의 기존 설정도 그대로 따른다.

```sql
-- 개발 프로젝트 확인 및 기존 값 보관 후에만 적용.
SELECT key, value FROM app_config WHERE key = 'context_checkpoint_temporal_enabled';
INSERT INTO app_config(key, value, description)
VALUES ('context_checkpoint_temporal_enabled', 'true'::jsonb, 'Timestamped checkpoint v4 producer')
ON CONFLICT(key) DO UPDATE SET value = excluded.value, updated_at = now();
```

활성화 뒤 새 checkpoint 잡의 `summarizer_version`과 성공 여부를 확인한다. 큐 상태는 `app/services/jobs.py::_STATS_SQL` 기준으로 확인하며, 성공 replay로 해결된 조상의 dead 이력을 오류로 세지 않는다.

되돌릴 때는 먼저 설정을 `false`로 바꿔 v4 생산을 멈춘다. 이미 만들어진 v4 잡은 호환 워커에서 처리한 뒤 워커 코드를 되돌린다. 대기 잡을 삭제하거나 임의 재실행하지 않는다. 플래그 도입 전으로 복구할 때는 보관한 기존 설정을 복원한다. 운영 활성화와 운영 PR은 이 작업에 포함하지 않는다.
