# 운영 알림 정책

## 목적과 범위

15분마다 반복되는 정상 작업 요약과 동일 미해결 사건의 경보를 줄이고, 조치할 장애와 하루 한 번의 운영 점검을 구분한다. 기존 RevenueCat 처리, 성공한 replay 이력, 사용자 데이터는 변경하지 않는다. 새 모니터링 플랫폼이나 DB 테이블은 추가하지 않는다.

개발 기준은 `origin/dev`의 `6fb3ea72`이다. 조사 당시 개발 API의 실제 배포는 `88426e74`였으며 health/ready는 정상이었다. 소스 기준 비교와 배포된 API 실험 결과를 구분한다. `main`의 선행 기능 전체를 병합하지 않는다.

## 현재 반복되는 이유

- 워커는 매 15분 새 프로세스로 실행된다. `slack_notify`의 메모리 중복 억제는 다음 프로세스까지 유지되지 않는다.
- `worker/tick.py`는 실제 일기·푸시 작업이 있는 tick마다 정상 요약을 보내며, RC 미해결 건도 매 tick 다시 알린다.
- 전일 billable 집계는 UTC 04시의 네 tick에서 실행된다. 값은 `user_daily_stats.activity_date` 기준 사용자 quota 가중량이며 provider 실비가 아니다. 사용자별 현지 04시 경계 때문에 같은 activity date의 값이 이후에도 증가할 수 있다. 관측된 증감 원인을 늦은 적재나 rolling 24시간으로 단정하지 않는다.
- Slack 실패를 현재 호출자가 알 수 없고, 중복 억제 시각은 전송 전에 기록된다.

## 알림 분류

| 신호 | 경로 | 최초·지속·종료 |
| --- | --- | --- |
| 정상 tick의 작업 수 | 구조화된 내부 집계 | 매 tick Slack 전송 없음 |
| 일일 운영 점검 | status | KST 13시 이후 첫 성공 전송, 하루 한 번 |
| RC production/unknown 미해결 또는 처리기 장애 | alert | 최초, 의미 있는 변화, 지속 시 6시간 간격 |
| RC sandbox의 개별 미해결 사건 | status 점검 | 환경·개수·경과만 표시 |
| 워커의 실제 작업 실패 | alert | 최초, 의미 있는 변화, 지속 시 6시간 간격 |
| 관측한 사건의 정상 재관측 | 사건에 대응하는 경로 | 한 번 통지, idle tick은 복구 증거가 아님 |

모든 메시지에 앱 실행 환경을 표시한다. RC의 `PRODUCTION`/`SANDBOX`/`UNKNOWN`은 앱 실행 환경과 별개다. sandbox만 관측돼도 RC 처리기·DB·provider 자체의 장애를 낮은 중요도로 숨기지 않는다. 개발과 운영 상태 key는 분리한다.

sandbox 분류는 조치 우선순위만 바꾼다. failed/pending을 성공 처리하거나 지우지 않고 일일 점검 수에 그대로 남긴다. 원래 종결된 사건은 재처리하지 않는다. `held:provider_history_unavailable`과 확인된 RevenueCat read/transport 오류 prefix는 DB 내부에서 별도 집계하여 최근 pending도 환경과 무관하게 통지한다. 일반 소유권·과거 결제 검증 보류는 이 집계에 포함하지 않는다. 기존 held 코드가 외부 이력의 모호성도 포함하므로 이 신호는 ‘외부 이력 확인 불가’이며 provider 전체 장애 확정으로 표현하지 않는다.

변화 fingerprint는 RC 사건 집합과 상태를 DB에서 digest한 값으로 만든다. 개수만 같아도 새 사건을 구별하되, 경과 시간·재시도 시각의 변화는 새 사건으로 취급하지 않는다. 같은 중요도에서 변화가 잦아도 최소 1시간 간격으로 모아 보낸다. 중요도가 높아진 경우에는 기존의 짧은 5분 억제 간격을 적용한다. 전송 실패는 통지 성공으로 처리하지 않는다.

워커 일기·기억·시간 초과는 신호별로 관측한다. tick당 실패 1–4 / 5–19 / 20+의 세 구간으로 규모를 묶고 구간 상승은 5분 간격 후 재통지할 수 있다. 같은 구간의 단순한 수치 변화는 새로운 경보가 아니다. 메시지는 실패 수와 관측 결과 수를 함께 표시하며 전 사용자 실패율로 확대 해석하지 않는다.

개별 event ID, 사용자 ID, payload, 원문 오류는 Slack 요약·문서·검증 출력에 포함하지 않는다. 과거에 종결된 RC 사건을 재처리하지 않는다.

## 지속 상태와 전송 계약

기존 `app_config`에 정해진 신호별 `monitoring:alert:<app-environment>:<signal>` key만 사용한다. 날짜나 사건 ID를 key에 넣지 않는다. 일일 날짜는 값의 `last_notified_date`로 저장한다. 관측 상태, 마지막 성공 통지, lease token/만료 시각을 분리한다.

1. 짧은 DB 트랜잭션에서 관측 상태를 갱신하고 전송 대상이면 lease를 claim한다.
2. 커밋하고 DB 세션을 닫은 뒤 Slack을 호출한다. 네트워크 동안 row lock을 잡지 않는다.
3. Slack 성공 응답에만 같은 lease token으로 CAS ack한다. 늦게 끝난 이전 sender가 새 상태를 덮지 못한다.
4. Slack 실패나 webhook 미설정에는 성공 시각을 갱신하지 않는다. lease를 해제하거나 만료시켜 다음 tick에 재시도할 수 있게 한다.
5. DB 상태 저장 실패 시 actionable 경보는 기존 프로세스 내 억제를 거쳐 fail-open 전송한다. 일일 점검은 안전한 오류 로그를 남기고 다음 tick에 재시도한다.

claim 후 프로세스 종료는 lease 만료로 복구한다. Slack 성공 직후 ack 전에 프로세스가 종료되면 중복 전송될 수 있다. Incoming Webhook에 원자적 exactly-once를 보장하지 않는다. DB 장애 중에는 재알림 억제가 약해질 수 있으나 경보를 조용히 버리지 않는다.

RC의 미해결 0은 성공한 조회로 확인한 경우에만 종료로 처리한다. 워커는 이후 관련 작업의 성공을 관측해야 정상 재관측을 알린다. 새 실행의 성공을 과거 누락된 사용자 결과물의 복구라고 표현하지 않는다. 조회 실패는 0이나 정상으로 바꾸지 않는다.

전송에 실패한 사건이 그 사이 정상화돼도 조용히 버리지 않는다. ‘지연 통지 — 일시 실패 후 정상 재관측’으로 한 번 알린다. 관측 중 사건 번호와 통지한 사건 번호를 분리해, 이전 전송의 ack가 그 사이 발생·종료한 새 사건을 덮지 못하게 한다.

## 기존 구독 보너스의 불필요한 외부 심사

별도로 검토한 작은 보완은 이미 평생 지급된 동일 사용자·요금제에 대한 재심사만 생략한다. `_handle_active`의 소유권·결제 검증은 유지한다. 현재 결제의 기존 지급 연결이나 `granted`/`granted:refund_reversed` 사유는 최우선으로 보존한다. 연결이 없는 결제에서 현재 소유자와 결제 수신자가 같고 결제 요금제가 검증된 지원 값이며 동일 `(user, plan)` 지급 이력이 있을 때에만 `not_granted:user_plan_previously_granted`로 끝낸다. 회수된 지급도 평생 이력에 포함한다.

새 지급·차감·기존 지급 재귀속은 하지 않는다. 다른 사용자/요금제나 이력이 없는 경우의 provider 검증·보류는 유지한다. 이 변경은 이미 종결된 이벤트를 다시 처리하거나 구독 접근 권한 검증을 우회하지 않는다.

## 일일 운영 점검

- 제목은 `확인 필요`, `일부 관측 불가`, `관측한 항목에 미해결 없음`으로 관측 범위의 상태를 요약한다. 전체 서비스 정상 보증은 하지 않는다.
- 마지막 tick 완료 경과: 기존 heartbeat는 완료 시각이지 모든 작업의 성공 보증이 아님을 유지한다.
- 이전 워커·RC 처리기 실패 후 정상 실행 미확인: heartbeat와 같은 고정 key 조회에서 읽는다. idle tick도 이전 실패 확인 필요 상태를 지우지 않는다. 6시간 reminder는 실패가 다시 관측된 경우의 간격이며, 새 실행이 없는 동안에는 일일 점검에 미확인 상태를 남긴다.
- 큐의 ready/running 및 actionable dead 수와 제공되는 최장 dead 경과: `jobs.queue_stats`/`_STATS_SQL`의 성공한 replay 전체 조상 제외 규칙을 그대로 사용한다. 기존 해결 이력은 삭제·재실행하지 않는다. ready/running의 정체 시간을 추가 조회나 임의 추정으로 만들지 않는다.
- RC 환경별 미해결 수와 가장 오래된 경과, 처리기 관측 결과.
- 전일 KST 달력 날짜의 계측된 추정 USD와 미확정 호출 수.
- 각 항목을 읽을 수 없으면 해당 항목을 `관측 불가`로 표시한다. 당일 실패 수 0만으로 전체 정상이라고 쓰지 않는다.

비용은 전일 KST `[00:00, 다음 날 00:00)`를 UTC로 변환하고 `ai_usage_ledger.started_at`으로 집계한다. 기존 effective-dated 가격 catalog로 확정된 `cost_micro_usd`를 재사용한다. `NULL` 비용, started/failed/unknown_usage, 추정 cache write, 실험 행을 구분한다. 상한은 원장에 유효한 상한이 있는 부분에만 한정하며 미확정 나머지를 0으로 만들지 않는다. 원장 미계측 경로가 있으므로 회사 전체 비용이나 provider 청구 확정 금액이라고 부르지 않는다. billable 고정 임계 경보는 제거한다. 새 금액 임계값이나 트래픽 증가 장애 판정은 이 변경에 넣지 않는다.

## 수용 기준

- 독립 프로세스/경합 sender에서도 같은 사건의 정상 전송이 lease/CAS와 간격을 따른다. 정상 tick 여러 번은 Slack 0건, 일일 상태는 날짜당 성공 1건이다.
- 첫 장애, 동일 장애, 같은 개수의 새 사건, 중요도 상승, 지속 reminder, idle tick, 정상 재관측을 분리해 검증한다.
- Slack 실패·미설정, DB read/write 실패, claim 뒤 종료, ack 실패, 만료 lease, 늦은 ack에서 미통지 사건이 영구 억제되지 않는다.
- sandbox 개별 사건은 경보를 반복하지 않으며 sandbox 상태에서도 공통 처리기 장애는 경보한다.
- 성공 replay의 다단계 조상은 제외하고 새로운 actionable dead는 포함한다.
- KST/UTC 날짜 경계, NULL 비용, 일부 상한, 미계측·실험 범위, 집계 실패를 검증한다. quota 값은 USD로 표기하지 않는다.
- Slack은 mock/dry-run으로 검증한다. 실제 사용자 사례·원문은 검증 산출물에 넣지 않는다.

## 개발 통합과 배포 경계

구현 전 팀 교차 검토를 거친다. 단위 비교는 pinned `6fb3ea72` 전후로 수행하고 개발 API 비교는 배포 SHA별로 기록한다. 개발 Supabase에서 필요한 schema-only 및 합성 자료 검증을 하고 정리한다. 최종 개발 배포 전에 `88426e74`에서 최신 개발 소스로 넘어가는 선행 DB 계약도 확인한다.

조사된 최신 개발 Actions 실패는 실행 중 `Role=moly-backend-dev` 대상 0건에서 발생했으며 SSM 배포 전에 중단됐다. 현재 API 정상 여부와 별도 문제다. 기본 AWS 계정은 사용하지 않는다. 기존 프로젝트 GitHub OIDC 경로 이외의 접속을 추정하지 않으며, 재실행·배포는 단일 담당자의 통합 검증 이후에만 진행한다. 운영 변경·배포는 범위 밖이다.

`88426e74`→`6fb3ea72` 배포 차이는 3개 커밋이고 runtime 변경은 `subscription.py`에 한정된다. `db/`와 `app/models/` 차이는 없다. 개발 DB schema-only 확인에서 이 경로의 4개 테이블·필수 모델 컬럼 45개와 평생 지급 `(user_id, plan)` UNIQUE가 확인됐다. 이 확인은 데이터 정합성이나 모든 API 동작을 검증했다는 의미가 아니다.

지속 상태·RC 환경/외부 이력 분류·비용 날짜/미확정 처리·replay 조상·보너스 격리는 개발 DB의 합성 자료와 rollback으로 검증한다. RC/ledger/queue/grant는 실제 schema의 DEFAULT/CHECK를 복제한 transaction-local 임시 테이블을 사용하고, app_config는 자체 namespace만 만든 뒤 rollback 및 잔여 0을 확인한다. Slack/provider는 실행하지 않는다.
