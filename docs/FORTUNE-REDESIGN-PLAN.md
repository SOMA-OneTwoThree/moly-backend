## 1. 확정된 요구

- 총점과 연애·금전·직장·활력이 비슷하게 움직이는 인상을 해소한다. 계산 함수가 분리됐다는 사실만으로 완료하지 않는다.
- 총점이 높아도 특정 분야는 낮고, 반대 조합도 자연스럽게 나와야 한다. 매일 반드시 큰 차이를 강제로 만들지는 않는다.
- 한국어·일본어·영어 전체 총평, 풀이, 행동, 주의, 4분야, 행운색·UI까지 검수한다.
- 분야별 약 5문장 분량을 마침표와 정상적인 띄어쓰기가 있는 한 문단으로 읽히게 한다. 문장마다 엔터를 넣지 않는다.
- 한 문단 안에서 여러 관련 관찰·제안을 다룬다. 하나의 연락/구매 사례를 길게 늘이는 식으로 내용을 제한하지 않는다.
- 친근한 말투, 명확한 운세 판단, 구체적인 제안. 한국어 ~겠어, 흐름이야, 추상적 격려의 반복을 피한다.
- 이전 마침표 금지 요구는 최신의 문장부호 사용 요구로 대체됐다. 약 5줄은 모든 기기에서 고정 5줄이라는 뜻이 아니다.

## 3. 권장 점수 구조 — 제품 의미 변경을 포함하는 제안

### 3.1 점수의 의미

권장안은 다섯 축을 독립적인 결정적 콘텐츠 점수로 생성하는 방식이다. 날짜·생년월일이 같은 조건에서는 같은 결과가 재현된다. 외부 천체 신호의 강도 점수라는 기존 의미는 바뀐다. 실제 사건을 예측하거나 과학적으로 검증된 점수로 설명하지 않는다. 이 의미 변경을 숨긴 채 기존 계산에 난수만 덧붙이지 않는다.

천체 신호 기반 점수를 그대로 유지하려면 축별 신호·분포를 보정하는 대안이 있으나, 공통 신호 때문에 상관이 남는다. 이는 사용자가 요구한 분리 경험의 주안으로 선택하지 않는다. 이번 문서는 권장안을 구체화한 것이며 아직 적용하지 않았다.

### 3.2 계산 경로

1. 기존 사용자 현지 날짜 산정과 생년월일 검증을 유지한다. 시드에는 알고리즘 버전, ISO 생일, 현지 날짜, 축 ID를 명확하게 구분해 넣는다.
2. `overall/love/money/work/energy` 각각의 SHA-256 domain을 분리해 안정적인 균등 값을 얻는다. 날짜가 같으면 같은 결과이며 프로세스 hash, 런타임 random, 사용자 조회 순서에 의존하지 않는다.
3. 축별 값을 버전 관리하는 목표 분포의 역누적분포로 정수 0~100에 매핑한다. 이론상 독립적인 추출이라도 유한 표본의 상관은 0이 아닐 수 있으므로 실측한다.
4. 총점은 네 분야 평균·합계·보정 기준으로 사용하지 않는다. 한 축의 값을 바꿔도 다른 축 값은 달라지지 않아야 한다.
5. 일일 최저/최고 차이를 맞추기 위한 재추첨, 정렬, 한 분야 강제 하락을 넣지 않는다. 이런 사후 처리는 다시 분야를 연동시킨다.
6. 점수 시드와 문구 선택 시드를 분리한다. 문구 수정, 언어 변경, 과거 열람/광고 상태가 점수에 영향을 주지 않게 한다.
7. 성별, 출생 시각, 계정 UUID는 이번 점수 입력에 추가하지 않는다. 기존 성별 수집은 유지하되 점수에 사용한다고 설명하지 않는다. 같은 생일/현지 날짜의 사용자는 같은 점수를 받는 정책이다.

분포 초기 설계안: 0~9부터 90~100까지 구간별 확률 1/2/4/7/12/18/22/18/11/5%. 50점으로 고정되는 fallback은 제거하고 정확히 0·100은 드물게 한다. 이는 아직 시뮬레이션으로 통과를 확인한 분포가 아니며 구현 시 훈련 표본에서 조정 후 별도 검증 표본으로 확정한다.

### 3.3 총평과 분야 해석

화면의 종합 점수는 네 분야의 평균이 아니라 별도 ‘오늘의 운세’다. 설명 문구·도움말도 합산 점수로 오해되지 않게 검토한다. 총평은 하루의 태도·선택·우선순위를 다루고 ‘모든 일이 잘 풀린다’처럼 네 분야의 상태를 대신 단정하지 않는다.

분야 문구는 해당 분야 점수만 따른다. 총점 90·금전 20 조합에서 금전 조언을 긍정적으로 보정하지 않는다. 운세의 내부 reading code, 주제·맥락 판정과 행운색도 새 점수 체계에 맞춰 재설계한다. 예전 천체 해석 코드를 의미 없이 남겨 점수의 근거인 것처럼 사용하지 않는다.

## 4. 점수 검증 계획

고정 회귀 표본을 포함하고, 생일과 조회일을 분리한 학습/검증 세트를 준비한다. 기본 200개 생일 × 366개 날짜(73,200개), 추가로 다른 연도·윤일·시간대 경계·미래 연도·성별 불변성을 검사한다. 실제 사용자 DB에서 생일을 추출하지 않는다.

초기 합격 목표(아직 미검증):

- 10개 축 쌍 모두 Pearson 및 Spearman 절댓값 0.08 이하. 생일별·조회일별 상관도 분리해 집계한다.
- 각 분야 정확히 50점 비율 3% 이하, 표준편차 18 이상.
- 분야 최고·최저 차이 10점 이하인 날 10% 이하, 25점 이상인 날 65% 이상.
- 총점 고/저 구간에 따라 각 분야 평균이 3점 이상 체계적으로 움직이지 않는지 확인한다.
- 축별 10구간 빈도와 조건부 분포를 기록한다. 전체 상관 하나로 비선형 종속을 놓치지 않는다.
- 전 축 고점/저점, 비슷한 날, 크게 갈리는 날 모두 존재할 수 있다. 특정 날짜 결과를 강제 조작해서 지표를 통과시키지 않는다.
- API 재조회, 서버 재시작, 언어 변경, 문구 버전 변경에 점수 고정. 현지 날짜 변경 시 각 축 재계산.
- 낮은 점수에서도 재난·질병·파산을 단정하지 않는다. 확률 설계와 문구의 강도를 함께 검수한다.

- 한국어 학술 교정이나 중국어 중심 도구는 문체 목적이 달라 설치하지 않았다. ‘AI 감지 점수’를 품질 보증으로 사용하지 않는다.

`skill-creator` 절차로 개인 스킬 `moly-fortune-editorial`을 준비했다. 경로는 `/Users/brownie/.codex/skills/moly-fortune-editorial/SKILL.md`. 스킬 형식 검증을 통과했고 이 문서의 편집·검수 계획에 적용했다. 다음 턴부터 발견 가능한 로컬 스킬이며 서버 배포물은 아니다. 스킬이 모델의 언어 능력을 향상시켰다거나 원어민 검수를 대체한다고 주장하지 않는다.

### 언어별 기준

| 언어 | 작성 기준 | 별도 점검 |
| --- | --- | --- |
| 한국어 | 승인된 친근한 반말, 마침표 사용, 한 문단, 짧고 긴 문장 혼합 | 너/네 남용, 해봐/좋아 반복, 주술 호응, 번역투, 추상적 자기계발 표현 |
| 일본어 | 일본어 운세에서 자연스러운 판단·권유, 일관된 문체 | あなた 남용, だよ/してみて 반복, 조사·술어 연결, 과한 でしょう/かもしれない, 。/、 |
| 영어 | 자연스러운 회화체, 명확한 판단과 구체적 권유 | Today/You 반복, 직역 어순, 기업 홍보어, 운명 과장, 과도한 might/could, 문장 리듬 |

번역 순서: 축·점수대·긍부정 강도·2~3개 관찰·행동을 담은 의미 명세 → 한국어 문체 승인 → 같은 의미 명세를 보고 일본어/영어 작성 → 해당 언어만 읽고 자연스러움 검수 → 의미 대조. 한국어 5문장을 한 문장씩 번역하지 않는다. 직장/연인/질병 등 입력받지 않은 신상 정보를 사실처럼 단정하지 않는다.

외부 사전/맞춤법 도구는 필요 표현에 한해 사용하며 사용자 생일이나 전체 원고를 외부 교정 서비스로 보내지 않는다. 언어별 작성과 비평을 분리하되 이번 준비 단계에서는 별도 에이전트·원어민 검수를 수행했다고 주장하지 않는다.

### 분량과 내용 범위

기존 규모 유지: 언어별 총평 10구간 × 20묶음 = 200, 분야 4 × 10구간 × 20 = 800. 총 1,000개 단위 × 3언어 = 3,000개 단위이며 총평의 상세·해볼 것·조심할 것은 묶음 안에서 함께 관리한다. UI·색상 이름은 별도 목록이다.

한국어 분야는 약 5문장/공백 포함 180~260자를 초기 편집 범위로 두되 억지로 채우지 않는다. 일본어·영어는 글자 수를 직역 기준으로 맞추지 않고 같은 정보량과 읽는 시간을 기준으로 본다. 실기기에서 약 5줄인지 확인하되 작은 화면/큰 글꼴에서는 늘어나는 것을 허용한다. 강제 줄바꿈·잘림·말줄임으로 분량을 맞추지 않는다.

### 검수 합격 기준

자연스러움·가독성·분야 특이성·점수 적합성·적절한 확신을 각 5점으로 평가해 모두 4점 이상을 요구한다. 의미 반전, 결과 보장, 개인 사실 날조, 다른 축에 대한 단정, 누락된 번역/placeholder는 즉시 수정 대상이다. 평균 점수로 중대한 오류를 상쇄하지 않는다.

자동 검사는 중복 전문, 유사 구문, 첫머리/어미 빈도, 특정 단어 집중, 문장부호/엔터, ID/개수/해시를 점검한다. AI 문체 여부는 자동 점수로 확정하지 않고 의심 항목을 읽고 판정한다. 분야명과 점수대를 가린 검수, 20개 연속 읽기, 총점과 분야 점수가 반대인 조합 검수를 포함한다.

## 6. 실제 구현 시 파일·호환성 작업

| 작업 | 주요 파일/영역 |
| --- | --- |
| 독립 점수 생성·규칙 버전 | `fortune_rules.py`, `rules.v2.json` 또는 버전별 새 자산, `fortune_ephemeris.py` 점수 호출 의존 제거 검토 |
| semantic와 표현 경로 | `fortune.py`, `fortune_catalog.py`, `fortune_copy_selection.py`, `fortune_chat.py` |
| 3개 언어 문구·manifest | `copy.v2*.json`, `manifest.v2.json`, 승인/해시 생성 절차 |
| 본문 문단·길이 검증 | `app/schemas/fortune.py`, catalog validator, OpenAPI 및 SDK 설명/검증 |
| 앱 표시 | `fortune_result_panel.dart`의 `flow`/category `text` 합치기 |

현재 분야 text는 정확히 2항목, 총평 flow는 정확히 3항목이다. 앱은 각각 엔터로 연결한다. JSON 문구만 길게 넣으면 문단 요구를 만족하지 않는다.

호환 우선 제안: wire 배열 개수(분야 2, 총평 3)는 유지하되 각 항목을 ‘한 문장’이 아닌 ‘텍스트 구간’으로 정의한다. 분야의 5문장을 두 구간으로, 총평은 세 구간으로 나누어 보관하고 새 앱에서 한 문단으로 합친다. 일본어는 구간 사이 공백 없이, 한국어/영어는 정상 공백으로 합친다. 기존 앱은 구간 간 줄바꿈으로 보여도 역직렬화가 깨지지 않는다. 문장 개수·문장부호 제한 validator와 API 설명은 함께 수정한다. 외부 필드 구조 변경이 불가피하다고 밝혀지면 별도 계약 변경으로 다시 명시하며 조용히 배열 개수를 늘리지 않는다.

내부 규칙/문구 버전은 새 버전으로 올리되 기존 semantic 결과와 선택 이력을 읽는 호환 경로를 유지한다. 무조건 이전 점수를 새 의미로 재해석하지 않는다. 새 semantic 형식이 필요하면 내부 v4 어댑터를 추가하고 외부 API의 기존 필드·타입은 유지한다. 광고 해제, 구독 권한, 프로필 revision과 개인정보 삭제 규칙을 변경하지 않는다.

## 7. DB·배포·당일 결과

원칙: 새 테이블/컬럼 없이 기존 `daily_fortunes`의 score 결과 JSON, copy snapshot, rule/copy version을 사용한다. 다만 구현 시 실제 스키마 CHECK와 새 semantic 값을 재검증하고 DDL이 필요해지면 별도 변경으로 보고한다.

배포 당일 생성된 결과는 유지하고 다음 날짜의 새 결과부터 새 알고리즘/문구를 사용한다. `_current_row`의 copy/rule version 불일치만으로 강제 재생성하지 않는다. 기존 v3 당일 결과와 광고 잠금 해제를 읽을 수 있어야 한다. 같은 날 생일 변경 등 기존 무효화 동작이 발생하면 새 결과를 만들되 기존 광고 해제 보존 정책을 따른다. 문구 선택 회전 이력은 새 문구 묶음에 의미가 없는 ID를 무조건 이어붙이지 않도록 버전 전환을 검증한다.

기존 운세 대화 thread/context는 snapshot과 연결돼 있으므로 기존 대화는 기존 결과를 유지한다. 재계산 뒤 새 대화가 올바른 결과를 참조하는지도 테스트한다. 신버전 결과가 DB에 기록된 뒤 구버전 서버를 무조건 재배포하는 롤백은 금지하고, 신·구 결과를 읽는 호환 수정 버전으로 복구한다.

단계: 점수 시뮬레이션·분포 승인 → 낮음/중간/높음 및 혼합 점수의 소량 3언어 문체 승인 → 전체 작성/검수 → 서버·클라 호환 구현 → 기존 개발 환경 검증 → 모든 수정 완료 후 허가된 PR. 운영 DB·앱 출시는 별도다.

## 8. 준비 완료/미실행 구분

완료: 현재 원인·분포 수치 확인, 독립 점수 권장안, 언어별 작업 기준, 전용 스킬 형식 검증, DB/API/클라/당일 snapshot 영향 분석.

미실행: 새 알고리즘 구현·분포 목표 검증, 새 운세 문구 작성/수정, 독립 언어 리뷰, 기기 줄 수 검수, 테스트/배포/PR. 스킬 형식 통과는 문구 품질 검증 완료가 아니다.
