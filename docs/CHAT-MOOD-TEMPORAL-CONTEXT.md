# 오늘의 감정과 대화 시간 정보

## 오늘의 감정

사용자 시간대의 **오늘 달력 날짜(00:00)**에 선택한 감정 하나만 매 턴 읽는다. 활동일(04:00) 계산은 그대로 둔다.

```text
[User mood selection] 2026-09-15: 편안
```

- 앱의 5종 `annoyed`, `tired`, `neutral`, `content`, `excited`만 SQL에서 선택한 뒤 응답 언어의 앱 표시명으로 전달한다. 한국어는 짜증·피곤·평범·편안·신남이다. 미선택·미지원·조회 실패는 모두 `unknown`으로 표시하며 어제 기록으로 대체하지 않는다.
- DB에서 메모·작성/수정 시각을 읽지 않는다. 오늘 선택을 수정·삭제하면 다음 턴에 반영한다. 조회 실패는 savepoint 안에서 격리한다.
- 사용자 감정 일기의 본문·과거 조회 도구는 없다. 캐피가 쓴 발행 일기와 사용자 루틴 도구는 유지한다. 사용자가 대화에서 직접 말한 감정·사건도 기존 대화 이력으로 남는다.
- 고정 프롬프트는 사용자가 감정 이야기를 할 때만 선택값을 참고하고 현재 발화를 우선하도록 지시한다. 선택 이름만 묻는 질문은 짧게 답하며, 알 수 없는 앱 메모·과거 선택을 오늘 감정이나 캐피 일기로 대신하지 않도록 한다. 이 지시는 일반적인 감정 화제에서도 선택값 언급을 허용한다. 아래 관찰된 한계를 참고한다.
- 선택값을 전달할 수 없어도 `unknown` 한 줄을 유지해 삭제·미지원 값 변경 후 이전 값을 대체한다. `unknown`은 선택값을 모른다는 뜻이며 기록 부재를 뜻하지 않는다.
- 앱의 감정 일기 저장·조회·삭제 API와 DB 스키마는 변경하지 않는다.

## 시간과 캐시

배치는 `고정 프롬프트 → 고정 시각이 붙은 과거 대화 → 현재 시각·오늘 감정 등 휘발 system 블록 → 현재 사용자 발화`다. 서버 감정 블록을 대화 메시지나 기억으로 복제하지 않는다.

- 감정 블록은 약 **10–13 추정 토큰**인 한 줄이다.
- 과거 메시지에 상대 경과 시간을 매번 갱신하지 않는다. 같은 분의 연속 메시지는 시각 표식을 공유한다. 기존 40개 메시지 리셋·20개 보존 정책을 유지한다.
- 현재 시각과 마지막 턴으로부터의 경과 분을 별도로 제공한다. 오래된 배부름·졸림·이동 중 상태를 먼저 언급하거나 조언 근거로 쓰지 않도록 한다. 임의의 수명으로 기록을 삭제하거나 상태가 끝났다고 단정하지 않는다.
- 지난 사건·부상 안부와 자정 직후 이어지는 대화는 허용한다. 회상 기억의 근거 발화 시각은 언급 시각이며, DB 생성 시각을 사건 시각으로 사용하지 않는다.

토큰 수는 기존 런타임의 문자 기반 추정이며 실제 토크나이저 수치와 다르다. 고정 프리픽스의 캐시 배치는 유지한다.

## 검증 결과와 알려진 한계

- 단위 테스트 2,501개 통과. 감정 조회 범위·시간 경계·휘발 블록 배선·메시지 저장 제외·요약 v3/v4 호환을 포함한다.
- 기존 개발 Supabase 통합 테스트 13개 통과. 5종 감정·언어별 표시명·미지원 값·사용자 격리·수정/삭제·다음 날짜·조회 실패 복구를 확인했다. 메모나 작성/수정 시각이 달라도 전달값은 같다. fixture는 롤백했다.
- 개발 커밋 `9ada01a774ca83c4011ee14941bb3c22b533d4ad`에서 43개 응답을 직접 읽고 에이전트와 검토했다. 선택 조회·갱신, 메모/과거 선택 비제공, 현재 발화 우선, 대화 기억, 감정에 맞는 이야기 요청을 확인했다. 선택 조회의 `편안.` 같은 답변은 다소 건조하고 일부 이야기의 문장 연결도 어색했다.

일상적인 표현을 추가한 **9개 응답에서는 사용 범위의 한계가 확인됐다.** 오늘 `짜증`을 선택한 상태에서:

| 사용자 발화 | 실제 응답에서 관찰한 내용 |
| --- | --- |
| 나 오늘 기분 안 좋아? | “오늘 기분을 짜증으로 골랐구나.”라며 선택 사실을 직접 언급한 사례가 있었다. |
| 나 오늘 기분 안 좋아. | 사용자가 짜증을 직접 말하지 않았어도 짜증을 포함한 응답이 두 번 나왔다. |
| 피곤하다. | 두 응답 모두 피곤하다는 말에 반응했고 짜증은 언급하지 않았다. |

따라서 **선택값을 직접 묻지 않아도 감정 화제에서 앱 선택을 드러낼 수 있다.** 선택값을 내부 배경으로만 사용한다고 보장하지 않는다. 앞선 43개 응답에서 문제가 재현되지 않았다는 결과를 모든 문맥의 준수로 확대하지 않는다. 이 사용 범위는 현재 코드에 남아 있다.

최종 버전의 두 검증군에서 사용한 임시 사용자 43명과 관련 행을 모두 정리했고 공용 설정은 변경하지 않았다. 표현 선택 근거는 [PR #276](https://github.com/SOMA-OneTwoThree/moly-backend/pull/276), 최종 검증과 한계는 [PR #278](https://github.com/SOMA-OneTwoThree/moly-backend/pull/278)에 기록한다.

## 개발 배포와 요약 버전

DB 마이그레이션과 운영 DB 변경은 없다. 현재 시각·오늘 감정 한 줄은 코드 배포로 적용된다. 과거 요약에 시각을 보존하는 v4 생산은 별도 플래그로 기본 비활성화한다. 새 소비자는 기존 v3와 v4를 각각의 해시·프롬프트로 처리한다.

백엔드와 워커가 순차 교체되므로 **모든 개발 checkpoint 소비자가 새 버전임을 확인한 뒤** 아래 설정을 개발 DB에만 적용할 수 있다. 이 PR 작업에서는 실행하지 않았다. `context_checkpoint_enabled`의 기존 설정도 그대로 따른다.

```sql
-- 개발 프로젝트 확인 및 기존 값 보관 후에만 적용.
SELECT key, value FROM app_config WHERE key = 'context_checkpoint_temporal_enabled';
INSERT INTO app_config(key, value, description)
VALUES ('context_checkpoint_temporal_enabled', 'true'::jsonb, 'Timestamped checkpoint v4 producer')
ON CONFLICT(key) DO UPDATE SET value = excluded.value, updated_at = now();
```

활성화 뒤 새 checkpoint 잡의 `summarizer_version`과 성공 여부를 확인한다. 큐 상태는 `app/services/jobs.py::_STATS_SQL` 기준으로 확인하며, 성공 replay로 해결된 조상의 dead 이력을 오류로 세지 않는다.

되돌릴 때는 먼저 설정을 `false`로 바꿔 v4 생산을 멈춘다. 이미 만들어진 v4 잡은 호환 워커에서 처리한 뒤 워커 코드를 되돌린다. 대기 잡을 삭제하거나 임의 재실행하지 않는다. 플래그 도입 전으로 복구할 때는 보관한 기존 설정을 복원한다. 운영 활성화와 운영 PR은 이 작업에 포함하지 않는다.
