# 몰리 백엔드 개발 현황판

이 문서는 **지금 어디까지 됐고 다음에 무엇을 해야 하는지**만 적는다. 최종 갱신 2026-08-07.

설계와 구현 상세는 다른 문서가 가진다. 이 문서는 그 결론만 요약한다.

## 1. 지금 상태

기능은 전부 만들어졌다. **앱이 쓰는 API는 운영 서버(`https://voice.moly.asia`)에서 이미 돌아가고 있다.**

다만 2026-08 들어 새로 만든 **대화·기억 구조는 개발 서버(dev)에만 올라가 있고 운영 서버에는 아직 반영하지 않았다.** 운영 서버는 그 이전 구조로 사용자 618명을 받고 있다. 그래서 지금 가장 큰 남은 일은 새 기능을 더 만드는 것이 아니라, 개발 서버의 구조를 운영 서버로 옮기는 것이다. 절차는 `docs/CUTOVER.md`에 있다.

로컬에서 돌아가는 테스트는 **1,451개**다(2026-08-07, `feat/diary-prompt-i18n` 기준).

## 2. 개발 서버와 운영 서버 비교

2026-08-06에 실제로 측정한 값이다.

| | dev(개발) | prod(운영) |
|---|---|---|
| `public` 스키마 테이블 수 | 53 | 25 |
| 인덱스 | 154 | 65 |
| 제약조건 | 272 | 105 |
| 함수 / 트리거 | 129 / 6 | 96 / 4 |
| `schema_migrations`(DB 변경 적용 기록표) | 있음 | **없음** |
| 사용자 | 3명 | 618명 |
| 대화 메시지 | 261건 | 34,532건 (= 17,266턴) |
| 일기 | 4건 | 7,959건 |
| 새 대화·기억 구조 | 적용됨 | 미적용 |
| FCM 푸시 · RevenueCat · 배치 워커 | 없음 | 있음 |

두 가지를 기억해 두면 전환 판단이 쉬워진다.

- **운영 서버에만 있는 테이블은 0개다.** 즉 전환할 때 지워야 할 테이블이 없고, 되돌려도 잃을 데이터가 없다.
- **운영 DB에는 DB 변경 적용 기록표(`schema_migrations`)가 없다.** 어떤 변경이 이미 반영됐는지 DB만 봐서는 알 수 없다. 조사 결과 운영 서버는 `20260729`까지 반영된 상태다. 전환 첫 단계에서 이 표를 만들고 여기까지 반영됐다고 기록해 둔다. 안 그러면 다음 사람이 같은 조사를 다시 한다.

## 3. 완료된 것

### 3.1 앱이 쓰는 API — 전부 구현·운영 중

계약 상세는 `docs/API_SPEC.md`가 가진다. 아래는 구현 여부만 본 목록이다.

기본 규칙: 인증은 `Authorization: Bearer <Supabase JWT>`(웹훅 제외), 에러 형식은 `{error:{code,message,details}}`, 하루 경계는 각 사용자 지역 시각 04:00(`activity_date` 컬럼), 재화·토큰·구독 값의 기준은 서버다(앱이 DB에 직접 쓰지 않는다).

| 영역 | 엔드포인트 |
|---|---|
| 시스템 | `GET /health` |
| 대화 | `GET /chat/state` · `GET /chat/messages` · `POST /chat/messages` · `GET /chat/greeting` |
| 일기 | `GET /diaries` · `GET /diaries/{id}` · `GET /v2/diaries` · `GET /v2/diaries/{id}` · `POST /diaries/{id}/read` |
| 건초(앱 내 재화) | `GET /wallet` · `GET /wallet/transactions` · `GET /charging-station` · `POST /charging-station/attendance` · `POST /charging-station/routine-reward` |
| 광고 | `POST /reward-ad-sessions` · `GET /webhooks/ad-ssv` |
| 상점·꾸미기 | `GET /v2/shop/products` · `GET /v2/inventory` · `GET/PUT /v2/inventory/equipment` · `POST /shop/purchases` (v1 경로도 구버전 앱을 위해 남겨 뒀다) |
| 루틴 | `GET/POST /routines` · `PATCH/DELETE /routines/{id}` · `POST/DELETE /routines/{id}/complete` · `GET /routines/{id}/statistics` |
| 구독 | `GET /subscription` · `GET /subscription/plans` · `POST /webhooks/revenuecat` |
| 리뷰·문의 | `POST /review/prompted` · `POST /feedback` |

계정 관련 API(`/me`, 온보딩, 알림 설정, 탈퇴)는 **moly-auth**(Next.js)가 가진다. 같은 Supabase를 공유하며, moly-backend에는 사용자 조회용 읽기 헬퍼만 남아 있다.

`POST /chat/messages`는 `Idempotency-Key` 헤더가 필수다. 같은 키로 여러 번 보내도 결과는 한 번 보낸 것과 같다.

개발 서버에만 열리는 진단용 경로가 따로 있다(`/dev/...`). `enable_dev_routes` 설정이 켜져 있을 때만 등록되며, 기본값은 꺼짐이고 확인에 실패하면 요청을 거부한다.

### 3.2 대화·기억 새 구조 (dev에서만 동작)

**긴 기억은 같은 PostgreSQL 안의 pgvector 컬렉션 `vecs.moly_memories_v2`에 벡터로 저장한다.** 파이썬 패키지 `mem0ai`를 쓰지만 그 라이브러리의 기억 관리 기능은 쓰지 않는다. 벡터를 넣고 빼는 부분만 감싸서 쓴다(`app/services/mem0_adapter.py`). 별도의 외부 저장소는 없다.

이전에 쓰던 방식은 기억을 사실·근거·통찰 등 13개 테이블로 쪼개 저장하는 것이었다. 이 13개 테이블은 **전부 삭제했다**(`db/migrations/20260806_drop_legacy_memory.sql`, 개발 서버에 적용 완료).

| 무엇을 | 어디에 |
|---|---|
| 기억 본문(벡터 검색 대상) | `vecs.moly_memories_v2` |
| 지금 유효한 기억이 무엇인지 판정하는 상태 | `app/services/mem0_recall.py`가 읽는 기억 상태 표 |
| 어느 대화 턴까지 기억으로 만들었는지 | `messages.turn_seq`(대화 턴 번호) |
| 관계 단계 집계 | `user_relationship_states` |
| 프롬프트에 넣을 관계 문구 | `relationship_profile_renders` (미리 만들어 둔 결과만 읽어 쓴다) |

관계 관련해서 중요한 점: 관계 단계는 대화가 성공할 때마다 `user_relationship_states`에 쌓이고, 프롬프트에 들어가는 문구는 **미리 만들어 둔 `relationship_profile_renders`의 결과를 읽어서만** 쓴다. 대화 도중에 문구를 새로 만들지 않는다.

벡터 검색만으로는 부족해서, 검색 결과를 **지금 유효한 기억인지 판정하는 상태 값으로 한 번 더 걸러낸다.** 이게 없으면 사용자가 "이제 회사 안 다녀"라고 말한 뒤에도 캐피가 예전 직장 얘기를 계속 꺼낸다.

**캐피가 호출할 수 있는 도구는 두 개뿐이다**(`app/services/agent/tools/registry.py`).

| 도구 | 하는 일 |
|---|---|
| `recall_diaries` | 일기가 있는지, 몇 건인지, 목록과 전문까지 한 번에 가져온다 |
| `get_routines` | 특정 날짜 기준 루틴 목록과 그날 수행 여부 |

**대화로 기억을 지우는 기능은 없앴다.** 예전에는 `forget_memory` 도구와 `/memory` 계열 API가 있었지만 지금은 둘 다 없다. 기억 삭제는 **계정 삭제**로만 이뤄진다. 계정 삭제 시에는 `privacy_subject_barriers` 표에 차단 표시를 올려, 삭제가 진행되는 동안 그 사용자의 기억이 다시 만들어지지 않게 막는다.

`X-Moly-Capabilities: diary-reference-v1` 헤더를 보내는 앱이 일기 전문을 요청하면, DB 원문을 그대로 담은 카드가 응답에 붙는다. 카드를 받았다고 해서 일기가 읽음 처리되지는 않는다.

### 3.3 배치 워커

15분마다 한 번 실행되며, 각 사용자의 지역 시각을 보고 할 일을 정한다(`worker/tick.py`).

| 지역 시각 | 하는 일 |
|---|---|
| 04:00 | 그날 일기 생성(개인 일기 또는 캐피 자기 일기) |
| 09:00 | 아침 일기 알림 발송 — **현재 꺼져 있다** |
| 20:00 | 저녁 안부 알림 발송 |

여러 대의 워커가 같은 일기를 중복 생성하지 않도록 `diary_gen_claims` 표로 선점한다. 기억 만들기는 워커가 아니라 대화가 끝날 때 거는 별도 작업 큐(`async_jobs`)가 처리한다.

### 3.5 비용과 한도

대화 요금은 실제 청구액에 맞춰 계산한다. 입력·출력·캐시 읽기·캐시 쓰기에 각각 가중치를 곱해 하나의 값으로 합산하고, 그 값을 하루 한도와 비교한다. 가중치는 모델 제공사마다 다르며 모델 이름 앞부분을 보고 고른다(`app/config.py`의 `bill_weight_*`).

| 설정키 | 현재 값 | 뜻 |
|---|---|---|
| `daily_token_limit_free` | 20,000 | 무료 등급 하루 한도 |
| `daily_token_limit_trial` | 100,000 | 체험 등급 하루 한도 |
| `daily_token_limit_subscriber` | 100,000 | 구독자 하루 한도 |
| `free_launch_token_limit` | 150,000 | 런칭 무료기간 동안 전원에게 적용할 한도 |
| `free_launch_until` | `2026-09-01T04:00:00+09:00` | 런칭 무료기간 종료 시각 |
| `token_warning_threshold` | 8,000 | 남은 양이 이 값 이하면 앱에 소진 경고를 보낸다 |
| `diary_min_user_chars` | 60 | 개인 일기를 쓸지 결정하는 사용자 발화 글자 수 기준 |

이 값들은 전부 DB의 `app_config` 표에서 덮어쓸 수 있다. `app/config.py`의 값은 DB에 값이 없거나 잘못됐을 때 쓰는 대비값일 뿐이다.

### 3.6 유저에게 보이는 글의 언어 (2026-08-06 정리)

서버가 만들어 내보내는 글은 한국어·영어·일본어 셋뿐이고, 그 밖의 언어를 쓰는 유저는 영어를 받는다. 구조 설명은 `docs/ARCHITECTURE.md` 5.7절에 있다. 이날 들어간 것은 다음과 같다.

| 무엇 | 어떻게 |
|---|---|
| 응답에 섞이던 다른 나라 글자 제거 방식 전환 (#173) | 지울 글자 계열을 나열하던 것을 **남길 계열을 나열하는** 쪽으로 뒤집었다. 유니코드 문자 계열이 150종이 넘어 지울 목록은 완성될 수 없었고, 목록에 없던 그리스·구자라트·키릴 글자가 그대로 나갔다 |
| 응답 끝에 공백 없이 붙는 라틴 조각 제거 (#174) | 라틴 문자는 어느 언어에서나 정상 글자라 위 방식으로는 못 잡는다. 마지막 한글 바로 뒤에 공백 없이 붙은 경우만 지운다(`strip_trailing_latin`). 공백으로 띄어진 것은 정상 끝맺음과 구분할 수 없어 건드리지 않는다 |
| 영어 이름 `Cappy` 고정, 한국어·일본어가 아니면 영어로 통일 (#175) | 예전에는 유저의 원본 언어 태그를 프롬프트에 그대로 넣어 중국어 유저에게 중국어로 답했다. 푸시와 서버 문구는 이미 영어로 나가고 있어서 한 유저가 화면마다 다른 언어를 봤다 |
| `profiles.language` 정규화와 기본값 영어, 영어 네이티브 페르소나 (#176) | DB 트리거가 저장 값을 `ko`·`en`·`ja`로 좁힌다(`db/migrations/20260806_normalize_profile_language.sql`). 컬럼 기본값도 `'ko'`에서 `'en'`으로 바꿨다. 영어 페르소나 `CAPI_PERSONA_EN`을 새로 썼다 |
| 저녁 푸시 개인화 철회 (#177) | v1·v2 합쳐 머지 8건을 전부 되돌렸다. `app/services/push_personalization.py`와 `push_personalizations` 테이블이 없어졌다. 저녁 20:00 푸시 자체는 남아 있고, 미리 정해 둔 고정 문구를 언어별로 골라 보낸다(`app/services/notify.py`) |
| 위기 대응 규칙이 세 언어에서 지워지지 않게 고정하는 테스트 (#178) | 페르소나를 언어별로 따로 쓰다 보니 한 언어에서만 규칙이 빠질 수 있다. 테스트로 막았다 |
| 일기 프롬프트 언어별 원본 (#179) | 일기 페르소나도 대화와 같이 언어마다 새로 썼다(`_DIARY_PERSONA_EN`·`_DIARY_PERSONA_JA`). **아직 머지 전이다** — 브랜치 `feat/diary-prompt-i18n` |

## 4. 기본으로 꺼둔 설정

전부 `app/config.py`에 있고 DB의 `app_config` 표로 덮어쓸 수 있다.

| 설정키 | 기본 | 켜면 어떻게 되는가 | 켜기 전에 필요한 것 |
|---|---|---|---|
| `agent_enabled` | 꺼짐 | 캐피가 `recall_diaries`·`get_routines` 도구를 호출한다. 도구 호출은 턴당 1라운드, 최대 3건으로 제한된다 | 도구 호출 한 턴당 응답 시간과 비용 확인 |
| `agent_canary_pct` | 0 | 일부 사용자에게만 먼저 도구 호출을 적용한다. 비용 상한이 아니라 대상 비율일 뿐이다 | `agent_enabled`가 먼저 켜져 있어야 한다 |
| `context_checkpoint_enabled` | 꺼짐 | 대화가 길어져 잘려 나갈 구간을 미리 요약해 두고, 다음 턴에 그 요약을 넣는다 | 요약을 반복하면 내용이 얼마나 뭉개지는지 측정 |
| `current_turn_context_enabled` | 꺼짐 | 프롬프트에 "지금 시각·함께한 일수·장착 아이템·오늘 루틴 진행"을 넣는다 | 프롬프트가 매 턴 바뀌므로 캐시 적중률 확인 |
| `current_context_last_active_enabled` | 꺼짐 | 위 블록에 "마지막 접속 후 얼마나 지났는지"를 추가한다 | `current_turn_context_enabled`가 먼저 |
| `morning_push_enabled` | 꺼짐 | 아침 09:00 일기 알림을 발송한다. 지금은 저녁 안부만 나간다 | 아침 알림 문구 확정 |
| `schedule_dispatcher_enabled` | 꺼짐 | 일기·알림 대상자를 예정 시각 인덱스로 찾는다(지금은 전체를 훑는다) | 두 방식 결과가 같은지 확인. 틀린 채로 켜면 그 사용자만 조용히 일기·알림을 못 받는다 |

기본으로 켜둔 것은 다음 세 개다.

| 설정키 | 하는 일 | 끄면 |
|---|---|---|
| `chat_prompt_cache_enabled` | 프롬프트 앞부분을 캐시해 비용을 낮춘다 | 대화 이력이 매번 새로 청구된다. 비용이 크게 오른다 |
| `turn_usage_v2_enabled` | 한 턴에서 일어난 모든 LLM 호출을 합쳐 한도에서 차감한다 | 대화 호출만 차감하고 나머지는 기록만 한다 |
| `memory_sweep_enabled` | 멈춘 기억 처리 작업을 자동으로 다시 시작한다 | 한 번 멈춘 사용자의 기억이 계속 멈춘 채로 남는다 |

이 외에 전환 중에만 의미가 있는 설정이 하나 더 있다.

- `privacy_barrier_mode` — 지금은 `compat`이다. 계정 삭제 차단 표에 해당 사용자 행이 없으면 그냥 통과시킨다. 과거 데이터를 다 채워 넣고 개수를 확인한 뒤에 `enforced`(행이 없으면 요청을 거부)로 올린다.

## 5. 남은 일

### 5.1 운영 전환 — 가장 큰 덩어리

절차 전체는 `docs/CUTOVER.md`에 있다. 여기서는 흐름만 적는다.

1. 운영 DB에 변경 적용 기록표(`schema_migrations`)를 만들고 `20260729`까지 반영됐다고 기록한다.
2. `db/migrations/`의 DB 변경 파일 `20260804*` → `20260805*` → `20260806*`를 **파일명 오름차순 그대로** 적용한다(총 27개). 파일명이 곧 순서다. `db/apply.py`는 기본이 미리보기이고 `--commit`을 붙여야 실제로 반영된다. 한 번에 하나씩, 미리보기로 먼저 본다.
3. 순서를 뒤집으면 안 되는 곳이 두 군데다.
   - **계정 삭제 차단** — `20260805_privacy_epoch.sql`(컬럼만 추가, 안전) → **코드 배포** → `20260805_privacy_active_backfill.sql` 순서다. 이전 코드는 차단 표에 행이 있으면 무조건 막는 것으로 읽기 때문에, 새 코드보다 먼저 행을 채우면 **전 사용자의 대화가 즉시 막힌다.**
   - **대화 턴 번호** — `20260806_backfill_turn_seq.sql`은 `messages.turn_seq` 컬럼을 만드는 `20260804_zzz_conversational_recall.sql` 뒤에 와야 한다. 파일명 순서가 이미 그렇다.
4. `scripts/preflight_cutover.py --env prod`를 다시 실행해 전 항목이 0인지 본다. 이 스크립트는 읽기만 하므로 언제 돌려도 안전하다. 전환 전 실행에서는 운영 데이터가 이미 전 항목을 통과했다.
5. 사용자를 새 구조로 옮긴다. DB 변경만 끝내고 두면 **전원이 기억 0인 상태로 대화하게 된다.** 이전 구조를 읽는 코드는 이미 지웠기 때문이다. `scripts/enter_shadow_cohort.py`로 한 명부터 옮기고, `scripts/verify_cutover_gate.py`로 그 사람의 기억이 실제로 쌓이는지 확인한 뒤 범위를 넓힌다. 적용 전에 `scripts/verify_shadow_entry.py`로 진입 경로가 살아 있는지 미리 볼 수 있다(트랜잭션을 열었다가 항상 되돌리므로 DB는 변하지 않는다).

비용과 소요는 이미 계산해 뒀다. SQL 반영 자체는 전 구간이 초 단위다. 실제 부담은 **과거 대화 17,266턴을 기억으로 만드는 작업**으로, 일회성 약 $14 · 약 7시간이다. 그 7시간 동안 기억 처리 큐의 슬롯 2개를 차지하므로 실시간 기억 처리가 그만큼 밀린다. 야간에 시작한다.

되돌리기는 비교적 안전하다. 테이블을 지우지 않으므로 데이터가 사라질 경로가 없다. 다만 `diaries` 테이블에 붙는 제약 3종과 `display_date NOT NULL`은 이전 코드와 함께 쓸 수 없다 — 되돌린다면 이 제약도 같이 내려야 한다.

### 5.2 회상 품질 기준 세트가 아직 없다

"어떤 발화에 어떤 기억이 나와야 맞는가"를 판정할 정답 모음이 아직 없다. 평가 도구(`scripts/eval_memory_golden.py`)와 기준값은 `evals/memory_golden_v1.yaml`에 만들어 뒀지만, 200건이 필요한데 **지금 들어 있는 것은 형태를 보여주는 예시 10건뿐**이다. 그래서 이 도구는 지금 의도적으로 실패한다. 무엇이 정답인지는 제품 판단이 필요해 자동으로 만들지 않았다.

이게 없어서 생긴 구체적 문제가 하나 있다. 벡터 검색 결과를 자를 때 쓰는 여유값 `RELEVANCE_MARGIN = 0.08`(`app/services/mem0_recall.py`)은 **개발 서버의 기억 12건으로 고른 임시값이다.** 한 대화에서 나온 12건이라 일반화할 근거가 없다. 이 값으로 "오늘 루틴 했어?"나 "여자친구랑 요즘 어때?"는 맞게 나오지만, **"안녕" 같은 내용 없는 인사에도 기억이 딸려 나온다.** 벡터 거리만으로는 "이 발화에 꺼낼 기억이 있는가"를 구분할 수 없어서, 임계값을 조정해 풀 문제가 아니다. 정답 200건을 채운 뒤 다시 정해야 한다.

### 5.4 탈퇴한 사용자의 기억 벡터 — 전환 작업에 포함할 것

**아직 확정된 문제가 아니다.** 코드만 읽고 의심한 것이라 실제로 그런지는 확인해야 한다.
따로 급히 고치지 않고, **어차피 기억 데이터를 전부 옮기는 전환 작업에서 함께 처리한다.**

의심하는 근거는 이렇다. 탈퇴는 moly-auth의 `backend/lib/account/service.ts`가 처리하고,
인증 사용자를 지운 뒤(`profiles`에 걸린 행은 연쇄 삭제된다) 기억 벡터를 직접 지운다.
그런데 그 부분이 `admin.from("memories")`인데, Supabase 클라이언트에 스키마 지정이 없어서
(`backend/lib/supabase/admin.ts`) 기본값인 `public`을 본다. 기억 벡터는 `public`이 아니라
`vecs` 스키마에 있고(운영 `vecs.memories`, 개발 `vecs.moly_memories_v2`),
`public.memories`라는 테이블은 이 저장소의 어떤 DDL에도 없다. 삭제 호출은 `try/catch`로
감싸여 실패해도 경고 로그만 남기므로 그냥 넘어간다.

전환 작업에서 이 순서로 처리한다.

1. **확인** — 기억 데이터를 옮길 때 주인이 없는 벡터가 있는지 센다. `vecs.memories`의
   `metadata->>'user_id'` 중 `profiles`에 없는 값이 대상이다. 0이면 의심이 틀린 것이고 여기서 끝난다.
2. **정리** — 나오면 옮기지 말고 지운다. 어차피 지워졌어야 할 데이터다.
3. **방어** — 앞으로 같은 일이 안 생기게 삭제 경로를 정한다. 지금은 moly-auth가 직접 지우는데,
   `vecs` 스키마에 클라이언트로 닿기 어려우므로 DB 함수나 moly-backend API를 거치는 쪽이 맞아
   보인다. moly-backend에는 차단 표를 세우고 정리 작업을 거는 구조가 이미 있지만
   (`privacy_subject_barriers`, `privacy_cleanup`) **부르는 곳이 없어 통째로 잠들어 있다**
   (`begin_subject_deletion`은 테스트에서만 불린다). 이걸 쓸지 새로 만들지 정해야 한다.

함께 볼 것: moly-auth는 삭제 차단 표를 세우지 않으므로, 삭제 중에 배치 작업이 돌면 지운 뒤에
기억이 다시 만들어질 수 있다. 3번을 정할 때 같이 본다.

### 5.5 코드에 남은 정리 대상

**"잊어줘" 시절의 세대 번호**가 남아 있다. `diary_recall_documents.suppression_generation`과 `chat_contexts.memory_generation`을 비교하는 조건이 여러 곳에 있는데, 그 값을 올리던 코드가 사라져 지금은 양쪽 모두 항상 0이다. 비교는 항상 참이라 동작에는 문제가 없다.

**일부러 그대로 두었다.** 이 조건이 SQL·작업 payload·요약 경계 검사까지 스무 곳 넘게 얽혀 있어서, 얻는 것 없이 위험만 큰 정리다. 나중에 손댈 때는 요약 작업이 오래된 결과를 버리는 로직을 함께 봐야 한다.

`db/schema.sql`에 이미 삭제된 테이블 **13개**의 생성문이 남아 있던 것은 **정리했다.** 이 파일은
문서가 아니라 새 DB를 만들 때 실제로 적용된다(`db/migrations/README.md`). 그대로 뒀으면 새
환경을 만들 때마다 없어야 할 테이블이 다시 생겼다. 생성 테이블이 50개에서 37개로 줄었고,
딸린 인덱스·제약·과거 데이터 이전 문장도 함께 걷어냈다.

### 5.6 문서 작업 중 찾아서 고친 결함 (2026-08-06)

문서를 코드와 대조하다 나온 것이다. 셋 다 개발 서버에만 해당하고 운영에는 없던 코드지만, **운영 전환 시점에 그대로 살아날 것들이었다.**

| 무엇이 문제였나 | 어떻게 고쳤나 |
|---|---|
| 일기 검색용 임베딩이 한 건도 만들어지지 않았다. 작업을 만드는 코드는 있는데 처리기가 없어서 집어 가는 즉시 죽었고, `recall_diaries`의 유사도 검색이 통째로 동작하지 않았다 | `worker/diary_recall_jobs.py`를 만들어 처리기를 등록. "만드는 곳은 있는데 처리기가 없는 작업"을 찾는 검사를 추가해 재발을 막았다 |
| 계정 삭제 시 벡터 정리 작업이 시작되지 않았다. 등록 코드가 `return` 뒤에 있었다 | `return` 앞으로 옮겼다 |
| 삭제된 테이블을 참조하는 조건이 `chat_references.py` 두 곳에 남아 있었다 | 조건을 제거했다. 원래 항상 통과하던 조건이라 동작은 같다 |

| 삭제 완료 표시 함수를 위치 인자로 불러 `TypeError`가 났다. 확정 트랜잭션 안이라 예외가 삼켜지고 잡만 재시도를 소진하다 죽었다 | 이름 붙인 인자로 고치고, 삭제 회차 번호가 없으면 조용히 넘어가지 않게 막았다 |
| `GET /chat/state`의 개인 일기 판정이 실제 게이트와 단위가 달랐다. 토큰 기준값을 가중 청구 토큰과 비교했는데 실제 게이트는 글자 수다 | 그날 유저가 쓴 글자 수로 판정하도록 고쳤다. 세는 범위를 일기 생성 쪽과 똑같이 맞췄다 |
| 기억 색인 작업이 다른 대기열의 시간 예산을 썼다 | `job_memory_timeout_s`로 바꿨다 |

⚠️ **`GET /chat/state`의 `personal_diary_eligible` 값이 달라진다.** 필드 이름과 형식은 그대로지만 판정 기준이 바뀌었으므로 iOS 쪽에 알려야 한다.
